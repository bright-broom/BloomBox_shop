# 自作注文の発送管理

2026-09-17。設計の正本は [ADR 0015](../architecture/adr/0015-native-fulfillment-operations.md)。Shopify用画面とは別の、自作注文専用の運用機能です。

## 操作と責任

`/operations/native-fulfillments` で状態別に検索し、詳細で配送先・商品・決済状態を確認します。担当者が準備開始、準備完了、保留、再開、取消、発送、追跡訂正、配達完了を登録します。操作は確認チェックが必須で、成功後は再読込して最新状態から次の操作を行います。

発送は「準備完了・注文確定・決済完了・1箱」の場合のみ許可します。返金中・一部返金・全額返金・複数箱・既存発送は拒否します。発送後の返金は配達済みの事実を消しません。取消は返金や在庫戻しを実行しません。[返金・取消手順](REFUNDS_AND_CANCELLATIONS.md)に従い、担当者が別途処理します。

2026-09-24から、発送前の注文に限り、詳細画面で**お届け希望日の変更**を登録できます（migration `0030`）。日付はこの画面で変更しても注文・お支払い・在庫は変わりません。購入者へ自動の連絡は送らないため、変更の合意と連絡は「顧客からのご相談」への回答で行います。適用条件・記録・手順は[取消・返金の運用](REFUNDS_AND_CANCELLATIONS.md)を参照します。

配送会社はヤマト・佐川・日本郵便。追跡番号の空白とハイフンを除去し、英字は大文字に統一します。追跡番号と発送日時は既存の顧客注文詳細に表示され、注文所有者以外には表示しません。配送会社への指示送信と自動追跡取得は含みません。2026-09-19から、発送の登録と同じトランザクションで購入者への発送のお知らせを予約します（取消・追跡番号の訂正・配達完了では送りません）。送信の有効化と手順は[取引通知](NOTIFICATIONS.md)。

2026-09-25から、お届け予定日が東京時間で今日から2日後以前（過ぎたものを含む）なのに未発送の確定注文があると、5分ごとの商取引ワーカーが障害Issueで知らせます（件数のみ）。発送か取消を登録すると外れます。対応は[障害対応E](COMMERCE_WORKER_INCIDENTS.md)、判断は [ADR 0015追記](../architecture/adr/0015-native-fulfillment-operations.md)。2日は地域別の所要日数（P0-07）が決まるまでの暫定値です。

## 権限と情報保護

- Googleの確認済み識別情報から登録済み担当者を特定し、専用の `native_fulfillment_operators` 権限をトランザクション開始時・終了時に確認します。通常の管理画面へ入れるだけでは発送操作できません。
- `DATABASE_NATIVE_FULFILLMENT_URL` は `database/roles.sql` の専用ロールを使用します。公開接続・担当者登録を自動では行いません。
- 一覧には住所・電話・メールを返しません。詳細だけ、Stripeの配送先スナップショットを復号して参照監査を残します。請求先住所を配送先として代用しません。参照監査の保存失敗時は情報を返しません。
- 更新は同一オリジン・厳密な入力検証・担当者権限が必要です。操作理由、追跡情報、版、担当者、時刻を監査に保存します。ログには住所・電話・本文を出力しません。

## 再実行・競合

同一担当者・同一リクエストID・同一内容の再実行は、最新状態へ再適用せず保存済み結果を返します。異なる内容へのID使い回しや古い版は競合として拒否します。発送・追跡・状態・監査を同じトランザクションで保存し、監査失敗でも全体を戻します。注文と決済もロックし、返金処理と競合した際に古い決済状態で発送できないようにします。

## 導入と復旧

1. バックアップと復元手順を確認し、隔離DBでmigration `0028`・`0030` と専用ロールを適用します。お届け希望日の変更には、専用ロールへの `order_gift_snapshots(delivery_date, retention_expires_at)` のUPDATE権限と `order_delivery_date_changes` が必要です。
2. 既存の1発送に複数shipmentがある場合、migrationは停止します。実データを削除して通さず、既存取引を調査します。
3. 対象環境の専用DB接続、暗号鍵、Google担当者紐付け、期限付き権限を設定します。
4. 本人ログインで権限の有無・期限切れを確認し、合成注文で準備→発送→顧客表示、追跡訂正、二重送信を検証します。本番の実注文を検証用に変更しません。
5. 問題時は専用権限または接続を無効化し操作を止めます。アプリを戻しても記録済みの発送・監査は消しません。外部で発送済みなら、DBの巻き戻しで未発送に戻しません。

## 検証範囲と残作業

単体試験で状態遷移・発送前提・追跡番号・重複・競合を確認。隔離PostgreSQLで専用権限、失効、監査失敗時の原子性、返金とのロック競合、宛先限定復号、ページ送りを確認します。実Google担当者・公開DBの接続、運送会社の実追跡、実機操作は別の公開前確認です。Issue #124はこれらの接続・運用確認が残る間は完了扱いにしません。

## 実施済み検証（2026-09-17）

- 隔離PostgreSQL 18（ローカル専用インスタンス・専用DB）で全18ファイル248件成功。追加した発送DB試験13件には二重/競合操作、返金との行ロック競合、権限の無効・期限切れ、セッション途中失効、監査保存失敗時のロールバック、宛先限定復号、日付とUUIDのページ送りを含む。既存顧客試験で、本人だけが単一発送と返金を閲覧でき、別顧客・複数履行では発送情報を返さないことも確認した。
- 認証・Origin・入力の境界とServer Actionの回復を25件追加。確認チェックのない送信、偽のoperator ID、重複項目、ファイル値、ブラウザー指定の発送日時、不正な版、他用途DBへのフォールバックを拒否する。失敗時のログへ生の例外や個人情報を出さず、再表示だけの失敗で保存済み結果を覆さないことを確認した。
- 実際の一覧/詳細コンポーネントを合成データでSSRし、同じフォームコンポーネントをReact 19で動かした隔離HTMLで表示確認した。アプリの認証迂回ルートは追加せず、DB・公開サイト・実注文への接続は行っていない。フォームの返答は競合/成功を返す合成応答であり、UI確認を実配送の証拠としない。
- Chromeの実効320px/1280pxで一覧・詳細を確認。32文字の追跡番号がカード外へはみ出す問題を既存`account-wrap`で修正した。ページだけでなくmain/section/form/dl/dd/addressのscrollWidth/clientWidthを比較し、修正後の横はみ出し0件。一覧のページ送りも既存の24px間隔を適用した。
- フォームで発送操作の選択、配送会社/追跡番号の入力、保留と取消の理由分離、確認必須、Enter送信、処理中の操作停止、競合メッセージ、成功後の操作停止を確認。React Action完了時の自動リセットで編集が消える問題は、入力の状態管理と明示的な送信処理で修正した。競合後も操作・配送会社・追跡番号・確認状態を保持する。
