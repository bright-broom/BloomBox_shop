# Migration履歴だけを読む接続ロール

2026-09-18。#121 / #122 の配備前確認用。公開DBのアプリ接続では履歴の読取権限が不足したため、アプリの権限を広げず、専用接続を用意する。既存の `bloombox_readonly` は全業務テーブルを読めるため、この用途には使用しない。

## 適用担当の作業

1. 対象環境・コミット・DB所有者を確認し、承認された変更作業として実施する。接続情報は秘密管理から環境変数等で渡す。URL・パスワードを文書、Issue、履歴に残さない。
2. ロール作成・対象台帳への権限付与が可能な所有者接続で `psql -X -v ON_ERROR_STOP=1 -f database/schema-reader.sql` を実行する。接続先は事前設定した保護付き接続を使う。SQLは台帳の存在を必須とし、migrationや業務データを変更しない。
3. 所有者が別途、認証方式・有効期限を管理した専用LOGINを発行する。LOGINには権限継承を有効にし、`bloombox_schema_reader` の所属だけを付与する。アプリ用・所有者用LOGINに流用しない。パスワードの作成・保管・所属付与はこのSQLの対象外。
4. 専用LOGINの実効権限を確認する。他ロールへの所属、PUBLIC由来の権限、他スキーマ、SECURITY DEFINER関数経由の操作も環境側で確認する。このSQLはDB全体の権限監査ではない。
5. 専用接続を秘密管理の `DATABASE_STATUS_URL` に設定し、[配備前確認](DATABASE_PREFLIGHT.md)を対象SHAで実行する。成功/未適用/権限不足を区別して記録する。接続先の発行や実行成功だけで販売開始可能とは判定しない。

## 権限と失敗時の扱い

NOLOGINの専用グループに、対象DBのCONNECT、`bloombox`のUSAGE、台帳の `version` / `name` / `checksum` 列のSELECTのみを付与する。`SELECT *` は許可しない。台帳の更新や顧客・注文の読取、スキーマ作成権限は付与しない。

同じSQLを再実行できる。既存グループのLOGIN属性、管理権限、他ロール所属、業務テーブル等の余分な権限を検出した場合はtransaction全体を中止する。既存権限を自動で取り消さない。失敗時は所有者が対象環境と既存用途を確認する。

これは独立した運用SQLであり、自動migrationには追加しない。現在のテーブル構成で検査するため、将来のGRANTやPUBLIC権限変更後も別途監査が必要。

## 検証と戻し方

隔離PostgreSQLで9ケースを検証：再適用、3列の履歴読取、台帳全列・顧客・注文の読取拒否、台帳の更新/削除拒否、テーブル作成拒否、既存ロールの属性/権限差異検出、台帳未作成時の無変更。

公開DBへの適用・専用接続の発行は未実施。変更を戻す場合は所有者が専用LOGINから本グループの所属を外し、秘密管理の接続を無効化する。他用途がないことを確認してから個別の付与権限とグループを撤去する。本番で `DROP OWNED` を使用しない。業務データの復元は不要。
