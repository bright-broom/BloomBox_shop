# 担当者権限の監査付き失効

2026-09-12。店舗別の管理権限を持つ担当者が、承認権限を失効させる内部コマンドを実装しました。失効と同時に、実施者・理由・対象の確認版を記録します。[ADR 0007](../architecture/adr/0007-operator-permission-revocation.md)を参照してください。[Googleログイン付き管理画面](OPERATOR_PERMISSION_MANAGEMENT.md)への後続接続も実装済みです。実管理者の指定と実権限の変更は行っていません。

## 管理できる人と対象

管理権限は承認権限とは別の `fulfillment_permission_managers` で管理します。検証済み担当者 UUID と店舗の組について、有効フラグ・期限・作成時刻を確認します。既定の本人確認アダプターは未認証を返します。既存の承認権限、購入者ログイン、リクエスト内の担当者IDだけで管理はできません。

権限の付与・再有効化・期限延長・管理者の登録はこのコマンドの対象外です。対象の承認権限を失効する機能だけを持ちます。店舗と対象IDの組、画面で確認した版、理由、冪等キーを検証し、理由は「担当不要」「役割変更」「セキュリティ対応」の固定分類です。自由記入による個人情報を監査へ持ち込みません。

## 同時操作と再送

1. 管理権限行を共有ロックし、対象の承認権限行を排他ロックします。既存の注文参照・承認が行う共有ロックと直列化するため、進行中の確認とは順番に処理されます。
2. ロックを取得した後のDB時刻で管理権限とセッションの期限を再検証します。確認版が変わった対象、無効な対象、別店舗の組み合わせは変更しません。
3. 対象を無効にして版を1つ進め、不変の失効記録とOPERATOR監査を同じトランザクションで保存します。既存のSYSTEMによる権限改訂監査も残します。監査の保存に失敗した場合は、無効化・版・失効記録もすべて戻ります。
4. 同じ実施者・キー・対象版・理由・管理権限版の再送は、現在の管理権限と対象状態を再検証して同じ履歴を返します。キーの使い回し、違う理由、管理権限の再付与後の古い判断は競合として停止します。失効後にDB管理者が再有効化した新しい版を、古い再送で無効化することはありません。

完了後の参照・承認は既存の権限確認によって拒否されます。すでに進行していた処理を巻き戻す機能ではありません。実行済みの発送や過去の承認履歴も変更しません。失効自体に外部通知・発送・Outbox作成は伴いません。

ロック待ち1秒・各SQL実行2秒の上限を設けています。DB障害・権限不足・保存状態の異常・タイムアウト時は停止します。結果不明時は同じキーと確認版で再送し、履歴と現在の版を確認してください。

## DB境界と適用手順

前進移行0016で管理権限、失効記録、失効専用のSQL関数を追加します。既存移行の内容は変更しません。移行後に `database/roles.sql` を再適用してください。

専用NOLOGINロール `bloombox_permission_manager` は管理権限・承認権限・失効履歴の参照と識別子列のロック、履歴／監査の追記、失効専用関数の実行だけを持ちます。一般アプリ・worker・承認用接続にこのロールを付与しないでください。新しいログイン資格情報や環境変数は今回作成していません。

失効専用関数は権限の作成・再有効化・対象変更・期限延長を行えず、指定した版の有効な権限だけを無効化します。SECURITY DEFINER を使い、検索先を `pg_catalog, pg_temp` に固定し、対象表はすべてスキーマ付きで指定しています。PUBLIC実行権限は関数作成と同じ移行トランザクションで取り消します。[PostgreSQLの安全な関数作成指針](https://www.postgresql.org/docs/current/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY)に沿った制限です。

専用DB資格情報自体は信頼境界です。SQL関数単独ではログイン本人や管理対象店舗を判定せず、アプリの管理者認可と実施者監査を含むトランザクションから呼びます。資格情報をブラウザー・公開処理に渡したり、関数をそのまま外部APIにしてはいけません。

管理権限の初期登録はDB所有者が別途行う必要があります。自動登録や実データの初期投入はありません。管理権限の改訂はSYSTEM監査に残りますが、初期登録の実施者まで記録する管理UIはまだありません。担当者と店舗の付け替え、履歴削除、版の巻き戻しはDBで拒否します。

## 検証と残件

通常667件・隔離PostgreSQL116件が成功しました。型・Lint・静的検査・本番ビルドと本番依存監査も成功しています。入力偽装拒否、6並列の同一再送、競合キー、別店舗／本人／期限の拒否、監査失敗の原子的な巻き戻し、再有効化後の再送拒否、実ロック待ち中の権限変更・セッション期限切れ、専用ロール、履歴不変性、既存参照への失効反映を検証しました。

上記は内部コマンドとDB境界の検証です。管理画面・Google認証とのリクエスト接続・共通の送信頻度制限は後続実装済みです。[DB所有者向けの登録・更新手順と運用ツール](OPERATOR_ACCESS_PROVISIONING.md)は後続実装済みです。実管理者の指定、実Googleと実店舗のE2Eは残件です。事業方針PENDINGや本番Gateは変更しません。

戻す際はこの管理コマンドの接続を停止し、前進移行・管理権限・失効記録・監査を保持してください。履歴を削除したり、失効した権限を一括で再有効化したりしません。誤った失効から復旧する場合は、別途承認したDB管理手順で新しい版として記録します。
