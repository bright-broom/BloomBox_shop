# 購入した顧客と注文の紐付け

[ADR 0009](../architecture/adr/0009-native-commerce-and-google-customers.md)の段階的移行です。商品DBへの移行に続き、購入開始時の認証情報を決済確定後の注文まで引き継ぎます。本番の新規注文受付は、実在庫・決済復旧・出荷の検証完了まで停止したままです。

## 所有者の決め方

1. サーバーが顧客専用Cookieの署名・有効期限・Googleクライアントと接続先・顧客の有効状態・認証の世代を確認します。ブラウザーが送信した顧客ID、メール、管理者アカウントは使いません。
2. Checkoutは購入準備に顧客IDと確認時の世代を保存します。初回保存のトランザクション内でも顧客の有効状態と世代を再確認します。受取人、ギフト内容、商品価格の既存スナップショットと同時に保存します。
3. 同じ購入操作の再送では、最初の顧客と現在の顧客が同じか確認します。別の顧客やログアウト後の再送は拒否します。同じ顧客が再ログインした場合は、現在の認証が有効なら同じ購入を継続できます。
4. 決済の開始・既存決済画面の再取得でも所有者を確認します。決済サービスへ送るのは既存の購入参照と商品情報で、顧客ID・Google識別子は追加しません。
5. 検証済み決済イベントの保存処理内で、Customerの専用窓口が購入準備から顧客IDを読み、購入者を作成します。購入者・監査記録・注文・入金記録等は同じトランザクションで確定し、途中の失敗はまとめて取り消します。通知の再送や同時処理で注文を重複作成しません。
6. マイページは購入者の顧客IDで注文を絞り込みます。決済サービス上の顧客IDやメール、配送先から注文の所有者を推測しません。

Customerが顧客アカウントと購入者の紐付けを所有し、Checkoutが購入準備の所有者スナップショットを所有します。PaymentはCustomerの公開契約を通して購入者を作成します。既存のStripe処理が担う注文・決済・配送情報の一括保存は維持しており、その全体を今回分離したわけではありません。

## ゲスト・失効・障害

- 未ログインの新規購入は従来どおり顧客IDなしです。Previewも永続顧客と紐付けません。今回は購入時のログイン必須化を行いません。
- ゲスト購入や過去の未紐付け注文を、後からログインした人へ自動で割り当てません。再ログイン後は新しい購入操作として開始します。
- 顧客認証やDBに障害が起きた場合、未ログイン扱いにして処理を続けません。
- 決済処理へ移った後のログアウトや顧客停止で、入金の事実を失わないようにします。遅れて届いた決済通知は最初の顧客IDを保持して記録します。停止中の顧客はマイページへアクセスできません。
- 所有者の不一致は専用の案内を返し、商品明細・個人情報・決済URLを返しません。

## DB適用と互換性

`0020_purchase_customer_binding.sql` を専用のマイグレーション権限で適用します。既存行の顧客ID・世代はNULLのままで、後付けの推定処理はありません。続いて `database/roles.sql` を適用します。注文の整合性検査のため、ワーカーへ購入者のID・顧客IDの2列だけSELECTを追加します。

購入準備の顧客ID・世代、購入者の顧客ID、注文の購入者IDはDBでも変更を禁止します。NULLからの割り当ても禁止です。顧客付き購入準備を、旧ワーカーが顧客IDなしの注文へ変換することもDBで拒否します。注文を別の人へ付け替える操作や、紐付いた顧客・購入者の物理削除は通常操作として提供しません。匿名化・保持期限の運用は別途レビューされた手順で扱います。

適用順序は、マイグレーション → 新しい決済ワーカー → 新しい購入処理です。古いワーカーは顧客IDを引き継がず、新しいDB制約で処理が停止するため、新しい購入を受け付ける前に全ワーカーの更新を確認します。本番の受付停止はこの変更では解除しません。

## 検証と残作業

専用ローカルDBで、同じ操作の並行再送、別顧客との競合、無効化・世代変更、顧客別の注文履歴、ゲストの未紐付け、決済通知の重複、決済保存失敗時の全体ロールバック、限定権限、DBでの所有者変更拒否を検証します。通常テストでは認証読取の障害、フォームでの顧客ID偽装、決済直前のログアウト、決済画面再取得の所有確認、外部送信情報の最小化を確認します。

これらは合成した認証・決済イベントと専用DBの検証です。実Googleアカウント2人とStripeテスト決済を通した接続確認、公開環境の設定、実在庫運用・出荷の接続は未完了です。在庫予約・解放・確定の内部実装は [NATIVE_INVENTORY.md](NATIVE_INVENTORY.md) を参照してください。

### 2顧客の履歴・注文詳細を通した回帰検証（2026-09-13）

購入準備の作成から決済イベント処理、購入者の紐付け、注文履歴、注文詳細までをつなぐDBテストを追加しました。顧客A・Bとゲストがそれぞれ購入し、同じ決済サービス上の顧客ID・メールアドレスを持つ合成イベントを交互に再送します。実際のアプリ用DBロールで、各顧客の履歴が本人の1件のみであること、本人の詳細を取得できること、相手とゲストの注文IDを直接指定しても詳細を取得できないことを確認します。確定注文は重複せず合計3件で、ゲストの所有者は未紐付けのままです。

これは実Google・Stripeの通信を置き換えた自動テストです。既存の顧客用ローカルOAuthには2人目のテストユーザーを追加しましたが、本人のパスキー確認を必要とするため、2人目の実ログインと実ブラウザーでの注文分離はまだ未完了です。メールアドレス・Google識別子・秘密値はこの記録とテストに含めません。

プレビューの購入処理は永続顧客と紐付けない設計です。今後、実ログインと検証用DB注文を組み合わせて画面の分離を確認しても、Stripeテスト決済を通した購入の証跡とは区別します。本番の受付停止や既存の認証・所有権チェックは変更していません。

検証結果：Node 24.21.0 / pnpm 10.23.0で `pnpm check:ci`（通常890テスト・静的検査・型・Lint・ビルド）が成功しました。実Google検証DBとは別の使い捨てPostgreSQLでDB専用191テストが成功しました。ローカルはPostgreSQL 14、CIはPostgreSQL 16です。

## 戻し方

新規注文受付を停止し、顧客紐付けを理解する決済ワーカーを残したまま、必要な画面・購入入口のみ戻します。進行中の顧客付き購入を、旧ワーカーへ戻すとDB制約により確定処理が停止します。旧版へ全体を戻す必要がある場合は、先にワーカーを停止し、進行中取引を確認してから、紐付け対応版で照合・確定します。

追加した列・トリガー・監査・顧客・注文情報を削除したり、所有者を書き換えたりしません。誤った紐付けが判明した場合は受付を止め、監査情報を保持して個別の是正手順をレビューします。
