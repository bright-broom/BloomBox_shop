# Shopify決済状態の照合・保存

2026-09-11時点。`ReconcileShopifyPayment`が正式な注文・取引データの取得、購入試行との関連付け、決済状態の検証・保存を行います。重複・遅延・取引更新を前提に、Payment所有の`shopify_payment_evidence`へ状態と検証根拠を記録します。

価格照合の追加: 決済保存後、同じ正式API応答の商品・送料・税・割引をOrder所有のルールで照合し、MATCHED/HELDを返します。価格不一致でも有効な決済観測は保存します。これは注文確定ではありません。[金額照合の仕様と残件](SHOPIFY_ORDER_PRICING.md)。

## この記録の位置付け

これは関連付け済みShopify注文の決済観測記録です。既存の`payments`は受け入れ済みローカルOrderへの外部キーと確定金額を必要としますが、税・送料・割引・配送・ギフトの最終受け入れはまだ完成していません。そのため、それらの値を仮造りしてOrder/Payment/Fulfillmentを作成せず、まず独立したPayment所有の照合結果として保持します。

`CAPTURED`の観測だけで注文確認・発送・返金の外部API操作は行いません。顧客への注文状態表示や会計台帳への反映も未接続です。将来の注文反映は、この記録と正式な最終金額・配送条件の両方を確認する必要があります。Shopifyが引き続き正式なcommerceデータの保有者です。

## 判定根拠

Admin APIの注文`transactions`を、親取引ID・種別・状態・金額・テスト区分とともに読みます。先頭101件を要求し、100件を超える場合や重複IDがあれば不完全な取引一覧として拒否します。返金通知の場合も、返金単体ではなく関連注文全体の取引一覧と受領/返金合計を照合します。[公式Order取引一覧](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/Order#field-Order.fields.transactions)、[取引と親子関係](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/OrderTransaction)。

成功したSALE/CAPTUREだけを入金額に、成功したREFUNDだけを返金額に集計します。APIの`totalReceivedSet`・`totalRefundedSet`との一致を必須にし、注文の表示用決済ラベルから入金を推定しません。保留・応答待ち・状態不明は処理中、ERROR/FAILUREは取引失敗として残し、現金移動に加算しません。[取引状態](https://shopify.dev/docs/api/admin-graphql/2026-07/enums/OrderTransactionStatus)。

| 状態 | 検証済み根拠 |
| --- | --- |
| PROCESSING | 成功入金がなく、未決済/処理中。単発の取引失敗を注文全体の終端失敗とみなさない |
| AUTHORIZED | 有効な与信残高があり、入金はまだない |
| PARTIALLY_PAID | 作成時注文合計の一部が入金済み |
| CAPTURED | 作成時注文合計が入金済み、成功返金はない |
| PARTIALLY_REFUNDED | 入金の一部が返金済み |
| REFUNDED | 実際に受領した全額が返金済み。未入金分まで返金したと解釈しない |
| CANCELLED | 成功した与信取消で残高がなく、入金・処理中取引がない |

注文の`cancelledAt`は別の事実として保持します。注文が取り消されても入金が残っていればCAPTURED等の状態を維持し、返金済みとは扱いません。与信取消後に別の成功入金が発生した場合はその資金移動を観測し、取消状態を理由に捨てません。この観測状態は既存の業務Payment状態遷移とは別です。

CAPTURE/VOIDには成功したAUTHORIZATION、REFUNDには成功したSALE/CAPTUREの親を要求します。親より多い引落し/取消/返金、成功した未対応種別、ゼロ額VOID、安全な整数の上限超過、注文作成時合計を超える入金・与信、合計不一致は保留です。注文編集・複数決済・特殊な親子関係は実店舗の証跡に基づく追加対応が必要です。0円注文も現段階では受け入れません。

## 重複・順序・障害

- 同じ取引内容はID順・UTC日時へ正規化して比較し、再実行で状態・版・監査/Outboxを増やさない。
- 同時INSERTで複数の一意制約が競合しても、既存レコードをロックして購入準備/店舗/注文を再照合する。別の関連付けに対する衝突は拒否する。
- 新しい観測で成功取引が消える、成功が処理中へ戻る、取引IDに対応する種別/金額/親が変わることを拒否する。
- 古い観測は、既知の成功取引の部分集合で金額が増えていない場合のみSTALEとして状態を維持する。古い日時なのに未確認の成功取引や取消が含まれる場合は保留する。
- 同じ注文更新日時でも取引が進む場合があるため、取引の同一性と成功事実の保持を検証して更新する。単純な日時比較だけでは入金を破棄しない。
- 状態、取引根拠、版、監査、Outboxは1つのDBトランザクションで保存する。Outbox書込が失敗した場合は状態更新も戻す。

正式データ取得はDBトランザクションの外で行います。Checkoutの関連付けとPaymentの観測保存はそれぞれの所有モジュールで確定します。後者が失敗しても有効な関連付けを削除せず、再実行で冪等に進めます。未実装の注文受け入れが残るため、この処理だけでInbox全体を処理済みにしません。

## 設定・移行・運用範囲

内部ワークフローは公開経路・定期処理・Inbox消費に未接続です。呼び出し側はテスト/本番の期待区分を明示し、注文と全取引の区分一致を検証します。現在の実行証跡は隔離した合成テストのみで、実店舗API・本番決済の有効化は行っていません。

0001〜0006を変更せず、`0007_shopify_payment_evidence.sql`を前進適用し、`database/roles.sql`を再適用します。PaymentテーブルはCheckoutの不変リンクの購入準備・店舗・注文の組合せを外部キーで参照します。WorkerだけにSELECT/INSERT/UPDATEを追加し、アプリの一般接続には書込権限を追加しません。新規依存・環境変数はありません。

保存内容は取引ID・種別・親ID・状態・JPY金額・テスト区分・日時のみです。生カートトークン、秘密鍵、住所、氏名、ギフト本文を保存しません。監査/Outboxには集計値と安全な識別子・版を載せます。金融記録の保持・訂正運用は、本番公開前に既存の会計/個人情報方針と合わせて確定します。

## 検証とロールバック

Domainテストで入金・与信・部分入金・返金・取消、親子関係、金額一致、成功事実の保持、同時刻更新、古い観測、テスト区分を確認します。実DBでは同時重複、逆順、成功の巻き戻し拒否、不正関連付け、Worker権限、Outbox失敗時のロールバックを検証します。既存Stripe/カート/関連付けのテストも継続します。

アプリ差分を戻す際もマイグレーションと保存済み金融記録を保持します。過去の成功取引を削除して整合させず、正式API・監査・照合結果を確認した専用の前進修正で対応します。次は最終金額・配送/ギフトの受け入れ、Order/Paymentへの反映、状態表示、未着通知照合・滞留/保持期限・実店舗E2Eです。
