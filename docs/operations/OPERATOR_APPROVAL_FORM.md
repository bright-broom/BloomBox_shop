# 担当者の承認フォーム

2026-09-12。[注文一覧](OPERATOR_FULFILLMENT_INBOX.md)から開く確認画面に、確認内容の記録フォームと Server Action を接続しました。事業方針 `FULFILLMENT_INTAKE_POLICY.approval` は **PENDING のまま**です。操作可能なフォームは表示せず、直接送信も拒否します。実 Google 接続・実担当者権限の登録や、発送実行は行っていません。

## 表示と送信の境界

- 検証済み Google セッション、明示的な担当者対応付け、店舗権限で確認対象を取得します。事業方針が承認済みで、表示用判定も承認待ちの場合だけ送信情報を発行します。表示判定は承認権限を与えません。
- 店舗・発送 ID・確認済み受付版・担当者 UUID・セッション期限・test/live 区分・サーバー発行の冪等キーを JWE に封入します。既存 AUTH_SECRET から目的と正規 Origin を分離して HKDF-SHA256 で鍵を導出し、jose の dir/A256GCM を使います。ブラウザーには平文の担当者 UUID や冪等キーを渡しません。
- 有効期限は発行から最大5分、かつ元のセッション期限までです。再ログイン・別担当者・別 Origin・区分違い・改ざん・期限切れでは使えません。在庫根拠の30秒期限を延長するものではありません。
- 明示的なチェック操作を必須にします。サーバーは現在のログイン、対応付け、正規 Origin、単一の確認情報とチェック値を検証し、追加の担当者・対象・版指定や重複フィールドを拒否します。Next.js の Server Action による Origin/Host 検証と既定の本文上限も維持します。
- 既存の専用 DB ロールと承認トランザクションへ渡し、現在の権限・受付版・入金・数量・在庫・配送情報・事業方針を再判定します。承認、監査、Outbox は原子的に保存されます。発送状態は変わりません。

暗号化は [EncryptJWT](https://github.com/panva/jose/blob/main/docs/jwt/encrypt/classes/EncryptJWT.md)、復号と登録済みクレームの検証は [jwtDecrypt](https://github.com/panva/jose/blob/main/docs/jwt/decrypt/functions/jwtDecrypt.md) を使用します。

## 再確認・再送

送信中は操作を無効化し、結果を読み上げ可能な通知として表示します。結果不明時は同じ画面の同じ確認情報で再送できます。二重送信は同じ冪等キーで処理し、現在の前提も再検証します。保存後の画面更新だけが失敗した場合は、保存成功を失敗として扱いません。ログは固定の障害分類だけを出力します。

「最新の確認画面を開き直す」は保存済みの照合結果と履歴を読み直します。Shopify の再取得や照合処理を起動する操作ではありません。在庫根拠が古い場合は、照合側で新しい受付版を保存してから確認し直す必要があります。確認情報の期限切れや別画面からの再送では、過去の判断が残っていても再確認・競合になる場合があります。承認履歴を確認し、別キーを使って同じ版の承認を作り直さないでください。

プレビューは架空データの説明表示だけです。フォーム、認証、承認コマンド、実注文 DB には接続しません。

## 本番有効化の残件

実 Google の接続とログイン E2E、担当者別の監査を伴う権限管理、事業条件の承認、操作頻度の制限、実店舗での承認済み条件下のブラウザー／プロバイダー E2E が必要です。操作頻度の制限は今回未実装です。セッション個別失効の制約は [Google ログイン](GOOGLE_OPERATOR_LOGIN.md) を参照してください。承認時の照合は保存済み根拠に対するもので、Shopify と DB の同時点を保証しません。発送コマンド・Inbox 完了・本番 Gate は別の実装／有効化対象です。
