# Shopify通知の受信と保管

ADR 0003の通知受付部分を実装。Admin APIによる正式データの読取・購入試行との関連付け・決済保存・注文受け入れ・発送受付は内部処理として実装済みですが、Inbox workerと公開注文参照への接続、未着通知の再取得は未実装です。[メタデータだけの滞留診断](SHOPIFY_INBOX_DIAGNOSTICS.md)で保存後の待機・失敗・保持期限を確認できます。本番公開判定は変更していません。

## 受付範囲と設定

`POST /api/webhooks/shopify` は初期状態で503を返します。隔離した検証環境でだけ、以下を設定して受付を試験します。本変更では店舗への通知登録や実環境の設定変更を行っていません。

| 設定 | 内容 |
| --- | --- |
| `BLOOMBOX_SHOPIFY_WEBHOOK_MODE` | 未指定/`disabled`は停止。`capture`だけ受付。その他は設定エラー |
| `SHOPIFY_STORE_DOMAIN` | 対象店舗の`*.myshopify.com`ドメイン。認証情報と同じ店舗を指定 |
| `SHOPIFY_WEBHOOK_SECRET` | 対象アプリの通知署名用秘密鍵。Storefrontアクセストークンではない。秘密管理から注入 |
| 既存のWorker DB・暗号鍵設定 | [データ基盤](../../database/README.md)の設定を利用。鍵とDBが利用できない場合は成功応答しない |

通知API版は`2026-07`固定です。`application/json`で、注文通知には`admin_graphql_api_id`と`updated_at`、返金通知には`admin_graphql_api_id`と`created_at`が必要です。通知側でフィールドを絞る場合もこの組合せを残します。API版の変更はコード・契約テストと合わせて行います。

対象は`orders/create`、`orders/updated`、`orders/paid`、`orders/cancelled`、`orders/fulfilled`、`orders/partially_fulfilled`、`refunds/create`です。それ以外は署名・店舗/API版の確認後に無視して200を返します。顧客データ開示・削除通知の処理は含みません。このエンドポイントをその処理の代わりに登録しないでください。

## 信頼境界と保存内容

生の本文バイト列からHMAC-SHA256を計算し、Base64署名を定時間比較します。JSONの再整形は行いません。本文はストリーム読み取り時に1,000,000バイトまで、読み取り時間は2秒に制限します。Content-Lengthを過小申告しても実際のサイズで拒否します。

Shopifyの署名対象は本文です。店舗名、通知名、イベントIDなどのヘッダーは独立した認証証拠ではありません。許可店舗とAPI版の一致はルーティング条件にすぎず、同じアプリ秘密鍵を複数店舗で使う場合は本文の店舗所有権まで証明しません。この制約から、`orders/paid`を受けても支払済みには変更しません。[公式署名仕様](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries)。

保存する暗号化ペイロードは、参照種別、GraphQL形式の注文または返金ID、本文中の更新/作成日時だけです。数値IDをJavaScriptの数値から復元しません。氏名、住所、メール、ギフト本文、カート秘密情報、金額、支払い状態は保存しません。通知ペイロードの参照形式は[公式Webhookサンプル](https://shopify.dev/docs/api/admin-rest/latest/resources/webhook#refunds-create)を参照しています。

重複キーは`(SHOPIFY, 設定済み店舗, SHA-256(本文))`です。署名されていないイベントIDや通知名を変えて再送しても、新規イベントにはなりません。同じ注文の同じ本文は通知名をまたいで1件にまとめ、本文が異なる更新は別に保持します。注文通知はすべて`shopify.order.changed`、返金通知は`shopify.refund.changed`です。本文日時で古い通知を破棄したり、入金状態を判断したりしません。

既存Inboxの一意制約と暗号化を利用し、新しいマイグレーションはありません。保存した時点では`PENDING`です。受信本文や署名をログに出しません。Stripeの受信・再照合・処理キューはStripeの設定済みアカウントに限定し、Stripe処理本体もShopifyイベントを拒否します。

## 応答・障害・保持期限

| 応答 | 意味 |
| --- | --- |
| 200 | 対象通知は永続保存済みまたは重複。対象外通知は無視。入金完了ではない |
| 400 / 415 | 署名、必須ヘッダー、JSON参照形式、Content-Type等が不正 |
| 408 / 413 | 本文の読み取り時間またはサイズを超過 |
| 500 | 設定/暗号化/DB/受信処理の障害。成功扱いにせず再送を受けられる |
| 503 | 受付停止中 |

Shopify用の消費ワーカーはまだ組み込んでいません。既存の保持期限ジョブは30日経過した処理済み/失敗通知の本文を削除しますが、`PENDING`は削除しません。したがって`capture`は期間を区切った隔離試験用です。検証後は受付を停止し、専用の試験DBを通常の試験データ廃棄手順で片付けます。本番での長期受付には処理・照合・滞留監視・保持期限の完成が必要です。既存の他経路と共用するDBを一括削除しないでください。

共用Inboxの取得・再試行処理では、[復元できない通知だけを再試行・FAILED管理に回す処理](PROVIDER_INBOX_RECOVERY.md)を実装しました。不正な1件で正常な通知のバッチ全体を止めません。この変更はShopify workerの接続やFAILED通知の手動再投入を有効にするものではありません。

ロールバックは`BLOOMBOX_SHOPIFY_WEBHOOK_MODE=disabled`で新規受付を止め、必要に応じて本差分を戻します。共有Inboxの履歴・暗号鍵・既存マイグレーションを削除しません。将来、注文反映を有効化した後の停止手順は別途定めます。

## 次の実装と確認条件

1. 設定済み店舗のAdmin API認証情報で参照IDを取得する内部処理は実装済み（[仕様](SHOPIFY_ORDER_READS.md)）。残件は実店舗接続の検証。ヘッダーや購入準備ID属性だけで注文を関連付けない。
2. 永続化したShopify購入試行との対応、商品・数量・通貨・価格・注文所有権を照合する。失敗・不一致は保留し、注文や入金を作らない。
3. 重複・遅延・順序逆転・返金先行・部分返金を考慮し、注文/支払い/配送状態、監査、Outboxをトランザクションで反映する。
4. 未着通知と結果不明の再照合、失敗通知の復旧、保持期限・監視、署名鍵ローテーションを完成する。
5. 隔離店舗で実通知、再送、拒否、返金を試験する。ローカルの合成署名テストだけでは実店舗接続の証跡にならない。

## 検証

署名改ざん、UTF-8・空白の保持、対象店舗/API版拒否、本文ID・日時検証、個人情報削除、未署名ヘッダー変更時の重複、受信上限・タイムアウト・切断・DB失敗を自動テストします。実PostgreSQLで同時重複、暗号化、Provider/店舗別の取得、古いロックの回収、再試行、古い処理担当の完了拒否、注文等を作らないことを検証します。既存StripeとShopify購入試行のDBテストも併せて実行します。
