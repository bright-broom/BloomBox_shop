# Shopify通知のテスト注文処理

`POST /api/internal/shopify-inbox`を追加しました。署名検証済みの保存通知から正式Admin APIを読み直し、購入試行との関連付け、決済証跡、注文受け入れ、決済反映、購入状態更新、発送受付の記録を既存の所有モジュール経由で進めます。初期状態は停止です。実店舗・実決済の試験、定期実行、販売開始を行ったものではありません。

## 有効化の条件

隔離したテスト店舗・DBでのみ使います。以下の設定だけでは販売条件の承認になりません。税込・日本全国配送とM/L価格は2026-09-12にユーザー確認済みです。注文PII保持日数・Shopify商品対応等の未確定条件が残り、注文受け入れポリシー全体はPENDINGのため、新規注文は保留されます。承認条件を別途確定・実装し、実店舗試験を終えるまで継続稼働させないでください。合成テストのAPPROVED条件を実環境にコピーしません。

| 設定 | 意味 |
| --- | --- |
| `BLOOMBOX_SHOPIFY_INBOX_MODE` | 未指定/`disabled`は503。`test`のみ有効。`live`等は設定エラー |
| `BLOOMBOX_RUNTIME_MODE` | `production`必須。永続アダプターを選ぶ設定であり、Shopify実決済の許可ではない |
| `SHOPIFY_INBOX_WORKER_SECRET` | この処理専用の32〜256文字・空白なし秘密鍵。既存Stripeの秘密鍵へのフォールバックなし |
| `BLOOMBOX_SHOPIFY_ADMIN_MODE` | `read`必須。外部APIへの書込は行わない |
| `SHOPIFY_STORE_DOMAIN` / `SHOPIFY_ADMIN_ACCESS_TOKEN` | テスト店舗に限定した既存Admin読取設定。API版は既存の2026-07 |
| `DATABASE_WORKER_URL` / DB TLS設定 | 既存の`bloombox_worker`権限を持つ隔離DB接続 |
| 暗号化設定 | 保存時の暗号鍵を含む既存のデータ保護設定 |

既存のDB移行と`database/roles.sql`を適用した環境を使います。この差分に新しい移行・権限・依存追加はありません。通知受付は別設定です。[Shopify通知受付](SHOPIFY_WEBHOOKS.md)と同じ店舗・DB・暗号鍵を使います。

呼び出し元は専用鍵を`Authorization: Bearer <secret>`ヘッダーで送ります。URL、リクエスト本文、ログに秘密鍵を入れません。認証前にDB接続・Shopify照会を生成せず、本文から店舗、注文、価格、本番モード、承認状態を受け取りません。GETでは実行できません。応答は`private, no-store`です。

## 処理完了と再試行

1回で対象店舗の通知を最大1件取得します。外部照会を順に実行する間に、後続通知の処理権限が期限切れにならないよう取得量を制限しています。既存のStripeは従来のバッチ上限を維持します。

正式APIの注文と取引がともにテスト取引であることを確認してから、決済を保存します。店舗・API版の不一致は照合前に拒否します。通知本文の入金状態や住所を信用しません。事業者から読むだけで、決済・返金・発送APIへの書込はありません。

Inboxの`PROCESSED`には、注文受け入れ済み、Payment反映、Checkout更新、Fulfillment受付記録のすべてが必要です。発送受付が永続化した保留判断は正常な記録であり、出荷許可ではありません。実際の発送、顧客通知、Outbox消費、全業務の完了を意味しません。

未承認条件・未入金・価格・配送等の保留は固定分類コードで保存し、[診断](SHOPIFY_INBOX_DIAGNOSTICS.md)で件数を確認できます。未承認条件、未入金、購入試行との関連付け不能、完了依存不足、外部/DB障害は処理済みにせず、既存の上限付き再試行へ戻します。独立した所有モジュールの先行コミットは残し、次回は不変の受け入れ記録から再開します。注文・決済・発送受付を作り直しません。ロック喪失・完了記録失敗も既存の処理権限確認と再試行に従います。

応答の`ok: true`は今回のワーカー呼出しが終了した意味です。`inbox`の`processed`と`retryScheduled`を区別してください。12回でFAILEDになった場合や設定/依存障害は500です。過去にFAILEDとなった通知は自動取得しないため、空の200応答だけで滞留解消を判断しません。[診断](SHOPIFY_INBOX_DIAGNOSTICS.md)と[原因解消後の確認付き再投入](WEBHOOK_RETRY.md)を併用します。恒久的な未関連・未入金・取消注文の業務解決は残件であり、FAILEDを入金取消や注文削除として扱いません。

## 停止・復旧・検証

停止は`BLOOMBOX_SHOPIFY_INBOX_MODE=disabled`。通知受付を止める場合はその設定も別途停止します。進行中の処理は設定変更で中断されないため、実行終了を確認します。コミット済みの注文・支払い・発送受付、履歴、暗号鍵、移行を消さず、コード差分だけ戻せます。再開前に診断で未処理・FAILED・保持期限を確認し、原因を解消して同じ注文を再照合します。

自動テストは専用認証・無効状態の無I/O、店舗/API版拒否、テスト限定、完了条件、途中失敗、再送、二重作成防止を対象にします。隔離PostgreSQLでは実際のworkerロールで照合を実行します。Shopify通信のみ合成応答で、実店舗の保護データ権限・遅延・決済手段・キャンセル・返金のE2E証跡を代替しません。

次は残る注文保持・複数箱等の条件確定、実店舗の権限/データ形状/各決済手段の試験、未着通知と恒久保留の解決、Outbox処理、監視と実行頻度の設計です。本番リリースGateは維持します。
