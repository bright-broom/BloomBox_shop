# Shopify決済引き継ぎの永続化

2026-09-11。ADR 0003の導入手順2を内部基盤として実装。本番購入画面には未接続で、`StartShopifyCheckout` は既定で停止する。環境変数だけでは有効にならない。Shopifyの正規通知・注文投影・所有権確認・実店舗試験の完成前に接続しない。

## 作成と再開

1. 永続化済みPurchaseIntentをサーバーで取得する。新規受付の停止を確認する。
2. PurchaseIntentの行をロックし、事業者をSHOPIFYへ固定し、1件だけの作成試行を記録する。店舗ドメインも固定する。DBトランザクションの外で初めてShopifyへ作成要求を送る。
3. 返された商品・数量・金額・参照・URLを既存アダプタで検証する。カートIDを暗号化し、試行のREADY化、PurchaseIntentのCHECKOUT_CREATED化、監査・Outboxを一つのトランザクションで保存する。
4. 保存完了後だけURLを呼出し元へ返す。返す値に完全なカートIDを含めない。ただしCheckout URL自体も秘密情報としてログや分析へ送らない。
5. 再実行時は保存済みカートを読み直す。返されたカートID、購入準備ID、API版が保存情報と異なる場合は停止する。取得失敗・売切れ・価格変更・店舗/API版変更を、新規作成や別事業者への切替で回避しない。

| 試行状態 | 意味 | 再実行 |
| --- | --- | --- |
| CREATING | 外部要求に先立って作成権を保存した | 別の要求には作成権を渡さない。開始から2分経過後の再アクセスではUNKNOWNにする |
| UNKNOWN | 通信失敗、保存失敗などで結果を確定できない | 自動再作成なし。正式な照合・運用手順の実装待ち |
| READY | 検証済みの完全なカートIDを暗号化保存済み | 同じ店舗から既知のカートを再取得 |

2分は外部処理の失敗やカート失効を断定する期限ではない。実行中の元の試行が遅れて正常結果を返した場合、その同じ試行IDだけがUNKNOWNからREADYへ確定できる。別の作成権の再割当て、タイムアウトによる試行削除、ブラウザからカートIDを渡す復旧APIは設けていない。

作成権保存後に受付が停止した場合も、保守的にUNKNOWNとして保持する。作成成功後に受付が停止した場合は、結果の保存を完了する。保存が実際には完了し応答だけ失われた場合、UNKNOWNの記録はREADYを上書きせず、次回は保存済みカートを再取得する。作成権の保存完了応答が失われた場合は外部要求を送らず、残ったCREATINGを保持する。

## 秘密情報・監査・競合

- `0005_shopify_checkout_attempts.sql` が試行表・状態/暗号化フィールドの整合制約・事業者の切替禁止を追加する。試行表はCheckoutの所有。IDは購入準備ごとに1件、店舗固定。
- カートIDは既存AES-256-GCMと鍵IDを利用。追加認証データに購入準備ID・試行ID・店舗を含め、別行への暗号文のコピーを拒否する。鍵は既存の秘密管理に置き、復号が必要な旧鍵を保持する。
- `external_checkout_id` はSHOPIFYでは常にNULL。暗号化済みの試行表が参照の正本であり、平文の旧カラムやOutboxへ秘密キーを流さない。CHECKOUT_CREATEDはカート作成の記録で、支払完了ではない。
- 監査とOutboxには購入準備ID・試行ID・状態・事業者だけを記録する。生のエラー、カートID、Checkout URL、宛名、メッセージは含めない。
- 既存Stripe経路も外部要求の前に同じPurchaseIntentの行で事業者を固定する。両経路の同時開始では一方だけが事業者を選択できる。従来の期限付きSessionワークフローへShopifyを渡すことも拒否する。
- Applicationロールは試行のSELECT/INSERT/UPDATE、Workerは調査用SELECT。ブラウザへの新規公開APIはない。所有権はUUIDを知っていることだけで証明しない。本番接続時に購入セッションと所有権の確認が必須。

## 保持と結果不明の扱い

Shopifyへ固定済みのPurchaseIntentは、24時間の「未開始の購入準備」削除対象から除く。購入準備の期限をShopifyカートや遅延決済の期限と同一視しない。未確定の記録を期限切れと誤認して個人情報を消すと、入金後の照合・配送ができなくなるためである。

これは本番の無期限保持方針の承認ではない。UNKNOWNの正式な照合、担当者への通知、カート/入金の結果を確定して終了できる手順、暗号化資格情報の失効・削除条件は本番接続前の残件。今回Outboxの配信consumerや定期照合ジョブは追加していない。キーが失われた試行、店舗やAPI版が変更された試行も、自動削除や新規作成で復旧しない。

## 導入・戻し方

- migration 0001〜0004は変更しない。0005を前進適用し、`database/roles.sql` を管理者権限で再適用する。新しい環境変数・依存パッケージは不要。
- 既存SHOPIFY行の平文カート参照が存在すると0005は失敗する。移行対象の秘密情報をログ出力したり、削除して進めたりしない。現行の本番無効構成にはそのような書込み経路はないが、導入先に存在するなら専用の暗号化移行が必要。
- 古いAPI版のカートは、新版へ無条件に切り替えない。既存試行のAPI版、店舗、照合方針を確認する。
- 本番公開のGateは変更していない。実店舗のカート・決済の作成、課金・返金は行っていない。
- 試行が存在しない環境ならコードを戻しても追加スキーマを保持する。試行が存在する環境では、受付を止め、暗号鍵・試行記録・事業者固定・Shopify向け保持除外を維持して前進修正する。旧WorkerのTTL処理をそのまま再導入しない。適用済みmigrationを削除・改変しない。

## 検証

隔離したローカルPostgreSQLで、migrationの二重実行、同時開始、プロセス再作成相当の新Repositoryからの再取得、DBトランザクション失敗、保存応答の消失、UNKNOWN記録失敗、古い試行への遅延応答、暗号文の取り違え・鍵違い、事業者競合、権限、保持除外を検証する。Shopify通信には合成Providerを使うため、実店舗での契約/E2E証跡とは区別する。

実行結果：`pnpm check:ci` 成功（通常267件成功、DB22件は別実行のためskip、型・lint・境界・ビルド成功）。隔離DBの `pnpm test:database` は22件すべて成功（既存7件＋新規15件）。migrationを2回適用し、履歴が重複しないことを確認。公開画面の変更はなく、ブラウザでの実決済試験は未実施。
