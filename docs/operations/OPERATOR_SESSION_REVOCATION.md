# 担当者単位のログイン状態の無効化

2026-09-12。登録済み担当者の全ブラウザーで、次の要求から再ログインを必要にする設定を追加しました。他の担当者のログインや店舗別権限を変更しません。[ADR 0006](../architecture/adr/0006-google-operator-login.md)の既存の認証設定を使用し、DB移行・新しい秘密変数・管理画面は追加しません。実アカウントの設定変更は行っていません。

## 仕組みと適用範囲

`AUTH_OPERATOR_BINDINGS` の各対応付けに、省略時0の `sessionVersion` を指定できます。0以上の安全な整数のみを受け付け、不正な設定では認証を停止します。

Googleで検証したログイン時に、現在の版と内部担当者UUIDを暗号化Cookieへ保存します。以後、セッションを読むたびに現在のサーバー設定との一致を要求します。担当者の版を増やすと、以前のCookieは、複製されたものや直前の閲覧で再発行されたものも含めて拒否されます。ブラウザーから版や登録先を送っても更新できません。版と内部UUIDはブラウザー向けのセッション応答に含めません。

対応付けの追加・削除・内部UUID変更でも、古いログインの継続を拒否します。未登録のGoogleアカウントは従来どおり登録用情報を確認できますが、初めて対応付けた後はもう一度ログインが必要です。店舗別の参照・承認・管理権限は、その後もDBで個別に確認します。

失効済みCookieでは、注文一覧・注文確認・承認画面・権限管理画面と、準備済みの承認／失効フォームの送信をDB接続前に拒否します。認証APIは空のセッションを返し、Cookieの削除を指示します。閲覧で15分の絶対期限を延長することはありません。

## 設定変更の手順

1. 秘密管理で、対象環境の検証済みGoogle subjectと内部担当者UUIDの組を確認します。登録されていない担当者のアクセス停止には、許可メールの削除を使います。
2. 対象の `sessionVersion` を現在値から1増やします。省略されている場合は0として扱い、1を明記します。他の対応付けと資格情報は保持します。整数の上限は `9007199254740991` です。上限時に0へ戻してはいけません。
3. 設定変更の実施者・時刻・対象の内部UUID・旧版／新版・理由・反映環境を非公開の変更記録に残します。アプリのDB監査には自動記録されません。実subject、メール、Cookie、秘密値を公開Git・PR・ログへ書き込みません。
4. 変更をすべての稼働プロセスに反映し、必要な再起動／再デプロイを完了します。古いプロセスを残さず、ロールバック先や災害復旧用の設定にも新版を保持します。反映前のインスタンスは古いセッションを受け付ける可能性があります。
5. 隔離環境の本人操作で、対象者の既存ブラウザーから参照・準備済みフォームの送信が拒否され、別担当者のアクセスは維持されることを確認します。対象者が改めてGoogleログインすると、新版で入れます。拒否画面のHTTP番号だけで成功を判定しません。

合成例（実値に置き換えた設定を公開しないこと）:

```json
[{"subject":"synthetic-subject","operatorId":"00000000-0000-4000-8000-000000000001","sessionVersion":1}]
```

一度使った版へ戻したり、版を省略して0に戻したりしません。対応付けを削除して再登録する場合も、非公開の変更記録を参照し、過去の最大値より大きい版を使います。旧版へ戻すと、有効期限内の古いCookieが再び使える可能性があります。同じ設定の再適用は冪等ですが、版をもう一度増やすと、その間の新しいログインも無効になります。

## 初回導入と復旧

この形式より前のCookieは版と内部UUIDを持たないため、自動補完せず拒否します。初回導入では既存担当者全員が一度ログインし直す必要があります。設定に `sessionVersion` をまだ書いていなくても、以後のログインは版0を持ちます。

認証コードを前の版へ戻す場合、旧コードはこの版を検証しません。先に `AUTH_OPERATOR_ENABLED=false` を全プロセスへ反映して入口を閉じ、必要なら `AUTH_SECRET` を更新して古いCookieと準備済みフォームを全体で無効化します。問題を修正したコードと失効後の設定を反映してから再開します。単に版を戻して復旧しません。注文・権限・承認・監査履歴を削除する必要はありません。

## 制約と検証

この設定は担当者単位の全セッションを対象にし、特定端末だけの失効ではありません。新たなログインの禁止、Google自体のログアウト、パスワードや多要素認証の再要求ではありません。Googleアカウントが侵害された場合は、許可メール・対応付け・店舗権限の停止とGoogle側の復旧も必要です。すでに認証された処理を途中で取り消すことはできません。

現在の少人数向け環境設定で運用できる方式です。全インスタンスへの即時反映や端末別失効が必要になったら、共有セッション台帳を別途設計します。Google側のアカウント変更通知、実Googleの同意・コールバック、実環境への設定反映確認は残件です。本番販売・発送承認のGateは変更しません。

検証は合成データで実施します。Auth.jsの実Cookie暗号化・セッションAPI・サーバー認証を通し、対象者の複数Cookieと更新済みCookieの拒否、他担当者の維持、登録先変更、古い形式の拒否、準備済みフォームの拒否を確認します。署名付き合成OIDCコールバックでは、新しいログインが現在の版を取得し、版と内部UUIDがセッション応答へ出ないことを確認します。これらは実Googleでの検証の代用ではありません。

今回の検証では `pnpm check:ci` の通常712件・静的検査・型・Lint・本番ビルドが成功し、本番依存監査で既知の脆弱性はありませんでした。DB表・ロール・クエリは変更していないため、隔離DBの120件はこの変更では再実行していません。画面変更はありません。
