# Shopify入金確認後の配送期限照合

2026-09-11時点。`ReconcileShopifyPayment`は決済観測の保存・金額照合に続き、Checkout所有の関連付け済み配送計画を読み、処理時点の希望日を再確認して`deliveryTiming`を返します。購入時に有効だった日付でも、非同期決済や通知遅延で準備時間が足りなくなるケースを保留します。

期限確認後の[配送先の構造・地域検証](SHOPIFY_DELIVERY_DESTINATION.md)も内部ワークフローに追加しました。地域方針は未承認で、注文確定・発送開始は引き続き未接続です。住所照会が成功した場合は処理後に期限を再確認します。

## 判定の範囲

`WITHIN_WINDOW`は既存の配送日選択ルール（Asia/Tokyo、最短3日後・最大60日後）を処理時点でも満たしたことだけを示します。新しい加盟店SLAを決めるものではありません。地域・住所・休業日・在庫・配送サービス・紹介特典資格の確認、注文の確定保存と発送への接続は未完了です。この値だけで注文を確定したり発送を開始してはいけません。

`HELD`では理由を区別します。

- 古い決済観測、キャンセル済み注文、全額入金前/返金済み、進行中の取引、未解決の金額照合。
- 配送計画が見つからない、購入準備が失効/放棄されている、購入者の詳細情報が削除済み/保持期限切れ。
- 既に注文へ変換済みの購入準備。既存注文は今後専用の注文/発送処理で扱い、古い希望日から再受け入れしない。
- 日付の不正、準備日数不足、予約範囲外。

希望日の変更、返金指示、購入者への通知は自動で行いません。日程調整/返金の判断・実行は残件です。

## 信頼境界と再実行

希望日はブラウザーや通知本文から読みません。Checkoutの`PostgresShopifyDeliveryPlanQuery`が購入準備・試行・店舗・注文の4つの識別子を保存済みの不変リンクと照合し、注文のcommerce providerがShopifyであることも確認します。既存のworker権限で、希望日・状態・詳細情報の有無・保持期限だけを参照します。氏名・住所・ギフト本文・カート認証情報を取得/復号しません。

決済記録を先に保存するため、配送期限不足や詳細情報の消失によって正しい入金を捨てません。関連付け不一致/存在しない配送計画は保留、DB障害は固定文言の型付きエラーとして伝播し、再試行を可能にします。決済保存失敗時には配送計画の照会に進みません。

DUPLICATEでも現在の時刻で再確認します。時計は配送計画のDB読取後に取得し、読取中に日本時間の午前0時を越えても古い締切を使いません。通知の発生日時・注文更新日時・ブラウザーの日時は現在の準備余裕の根拠にしません。古い観測(STALE)は先に保留します。CAPTUREDでも返金等の取引が進行中なら保留します。

購入準備の通常TTLはShopifyの決済期限と同一視しません。CHECKOUT_CREATEDのままTTLを過ぎても配送計画を読み、詳細保持期限と現在の配送余裕で判定します。保持期限ちょうど、または削除済みなら受け入れ可能な日付でも保留します。

これは内部ワークフローの一時的な評価結果です。DBロックで注文・決済・配送を一括確定する処理ではありません。将来の注文受け入れでは最新の決済版・購入準備・個人情報・配送条件を原子的に再確認し、Order所有の不変スナップショットを保存する必要があります。

## 検証・移行・ロールバック

- Domain: 日本時間の午前0時前後、最短/最長日の境界、年跨ぎ、不正日付・時計。
- 正式APIの合成応答から内部ワークフローまで: 通知内の偽日付を無視、処理中の日付変更、重複再確認、キャンセル/未入金/返金/返金待ち/古い観測/不正価格、詳細情報保持期限、照会障害と再試行、決済保存障害。
- 隔離PostgreSQL: 正しい4識別子だけで取得、別店舗/別注文/別試行/別購入準備の拒否、読み取り専用トランザクションと既存worker権限、削除済み詳細、権限エラーの安全な伝播と復旧。
- 通常テスト438件、DBテスト39件、`pnpm check:ci`成功。実店舗決済やブラウザーE2Eの証跡ではありません。

DB移行・環境変数・追加権限・依存の変更はありません。公開経路/Inbox workerには引き続き未接続で、本番Gateを有効化しません。ロールバックは今回の配送期限評価・照会と文書を戻し、既存の決済・監査・Outbox記録を保持します。
