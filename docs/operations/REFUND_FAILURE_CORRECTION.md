# 成功後に失敗した返金の訂正

2026-09-17 / Issue #136（P1-02）。実装・隔離DB検証の記録であり、実Stripeでの検証、返金条件・担当者の承認、本番配備を意味しません。

## 動作

Stripeが成功済みの返金を後から `failed` に訂正した場合、署名検証済みのWebhookを既存Inbox/Worker経由で反映します。返金を指示するAPIや新しい外部呼び出しはありません。

1. 支払行をロックし、返金ID・支払ID・通貨・返金額が保存済みの事実と一致することを確認します。
2. 返金を `SUCCEEDED → FAILED` に変更し、成功している他の返金だけを再集計します。
3. `REFUND` は削除せず、同じ返金IDに `REFUND_REVERSAL` を一度だけ追加します。元の売上／Stripe清算勘定と逆の符号で記録し、各取引をゼロ合計に保ちます。
4. 支払状態・返金額・状態遷移・監査を同じDBトランザクションで保存します。書込失敗時は全体をロールバックします。

全額返金の失敗後は支払確定に戻ります。他の成功済み返金があれば一部返金済みを維持します。未解決の異議申し立てがあれば `DISPUTED` を維持します。財務照合は元の返金と逆仕訳の純額を使用し、顧客の購入実績は既存の支払額集計から再計算されます。過去の購入時割引は変更しません。

注文・発送・在庫の状態は変えません。取消済みの発送は再開しません。失敗した返金は顧客へ届いていないため、担当者がStripeで確認して代替対応を判断します。支払確定への復帰を、新しい発送や顧客への請求の指示と扱わないでください。

## 重複・逆順

- 元の返金より古い通知は状態を戻しません。同じ状態の新しい通知は最終確認時刻を進めます。
- Stripeの時刻は秒単位で、同じ秒の通知は順序を確定できません。同時刻の成功と失敗は失敗を優先し、どちらの到着順でも同じ返金額になります。
- 成功通知が先に届けば返金＋逆仕訳、失敗が先なら返金未計上になります。純額はいずれもゼロです。
- `FAILED` の後により新しい成功通知が来た場合は矛盾として拒否します。古い成功通知の再送は無視します。
- 成功後の `pending` / `requires_action` / `canceled` は、この訂正経路には含めません。新しい矛盾通知は既存のWorker Incidentで調査します。
- 返金IDと取引種別の既存一意制約により、別のイベントIDによる重複通知でも逆仕訳は一件です。

## セキュリティ・障害の確認

L3変更として、既存の署名・提供元アカウント/モード検証と暗号化Inboxを維持し、ブラウザー起点の返金変更経路を追加しないことを確認しました。異なる対象・通貨・金額と未知の状態は境界で拒否し、支払ロックで同時通知を直列化します。既存の取引種別・返金ID一意制約とトランザクションで重複・部分適用を防ぎます。個人情報・秘密値を追加記録せず、監査にはイベント識別子と種別だけを残します。一般の支払遷移の許可は広げず、検証済み返金を集計する専用の純粋な判定として支払復帰を扱います。

## 確認・再処理

1. Stripe管理画面の返金ID・状態・金額を照合する。
2. [財務照合](FINANCE_RECONCILIATION.md) で `LEDGER_REFUND_MISMATCH` / `REFUND_TOTAL_MISMATCH` がないことを確認する。
3. Worker Incidentに残る既存の失敗通知は、原因解消後に [Inbox再処理手順](COMMERCE_WORKER_INCIDENTS.md) を使う。本文が期限で削除されている場合は同手順の制約に従い、DBや台帳を直接修正しない。
4. 監査の `payment.refund_reversed` と元の返金IDに対応する逆仕訳を確認する。通知の再送は新しい返金を作りません。

## 検証と影響

- 純粋な状態判定10件、隔離PostgreSQLの新規8件＋既存Commerce/財務10件、`pnpm check:static` が成功。
- 全額／部分返金、並行再送、別の成功済み返金の維持、同秒逆順、異議申し立て、顧客購入実績、金額・通貨・対象の改ざん、逆仕訳の書込障害と再試行を確認。
- スキーマ・環境変数・依存追加なし。財務台帳の取引種別は既存text列で、既存一意制約を再利用。
- 旧版の財務読取処理は `REFUND_REVERSAL` を集計しないため、訂正適用後に旧版へ戻すと照合差異が出ます。訂正記録は消さず、Workerを止めて原因を調査し、修正版へ進めてください。Webhook受信・販売停止の既存制御を維持します。
- 実Stripeのテスト決済→返金→失敗通知の一連の確認は #128、返金・返品の事業条件は #118、担当者のStripe権限は #120 に残ります。Issue #136 全体の完了とは区別します。

Stripe公式資料（2026-09-17確認）：[返金失敗と資金の返還](https://docs.stripe.com/refunds#failed-refunds)、[Webhookのイベント順序](https://docs.stripe.com/webhooks#event-ordering)。銀行から資金が戻ると返金が失敗状態になり、`refund.failed` が発行されること、Webhookの配信順序が保証されないことを前提にしています。
