# 復元できない通知の再試行

保存済み通知の復号・形式検証に失敗しても、同じバッチの正常な通知を止めないようにしました。対象はStripeとShopifyが共用するInboxの取得・再試行処理です。Shopifyのworker接続や本番販売は、この変更では有効になりません。

## 変更した挙動

従来は、まとめて取得した通知のうち1件でも復号できないと、取得トランザクション全体が戻りました。先頭付近の不正な通知が毎回取得され、正常な通知も進まず、不正な通知のattemptsも増えない状態になり得ました。

現在は、読取可能な通知と復元不能な通知を別の型で返します。復元不能な通知には、既存の取得ロックに対応するprovider・アカウント・イベント参照だけを保持し、ダミーの本文や途中まで検証したイベントを作りません。処理本体へ渡せるのは読取可能な通知だけです。

復号鍵の不足、破損した暗号文、不正なJSON、配列などオブジェクト以外の本文、削除済み本文、不正な必須メタデータや日時は、`ProviderEventUnreadableError`という固定コードで記録します。本文・鍵・暗号ライブラリのエラーをログや失敗コードに含めません。DBの最小参照情報自体が不正、または取得・失敗保存に障害がある場合は、安全に対象を特定・記録できないためバッチの失敗を上位へ返します。

## 再試行と復旧

- 通常の失敗と同じくattemptsを1回増やし、指数的な待機後に再試行します。既存の最大12回・最大待機3,600秒の設定を変更しません。
- 再試行中に正しい保持鍵が復旧すれば、同じ暗号文とイベント参照から復元し、通常処理へ進めます。新しい通知を複製したり、保存済み本文を書き換えたりしません。
- 上限に達した通知はFAILEDとなり、通常の取得対象から外れます。処理結果のfailed件数にも含まれるので、既存Stripe workerの恒久失敗検知と、[Shopify Inbox診断](SHOPIFY_INBOX_DIAGNOSTICS.md)から確認できます。
- 取得後にworkerが停止した場合は、従来の5分のロック回復に従います。別workerが取得し直した後、古いworkerが失敗回数や完了状態を上書きすることはできません。

復旧担当者は、対象環境で保持鍵が揃っているか、本文の保持期限・削除状態・形式を確認します。鍵設定の全面的な欠落でも上限は進むため、異常が広がっているときはworkerを停止して原因を直し、再開を判断します。FAILEDの自動再投入や権限付きの手動再投入はまだありません。通知の複製・本文の推測・DBへの直接の完了書込みで警告を消さず、正式APIとの再照合と監査付き復旧を別途進めます。

FAILED通知の本文は、既存の保持期限ジョブによって削除される場合があります。診断・復旧のために永久保存する変更ではありません。受信時の署名検証、provider/店舗の絞り込み、暗号化の参照結合、注文/決済の冪等性と認可も引き続き必要です。

## 検証と戻し方

変更前の隔離DBで、StripeとShopifyそれぞれの破損通知が正常な隣接通知まで止めることを再現しました。変更後は、混在バッチ、欠落鍵の復旧、12回の上限、形式異常、複数worker、取得後停止と古いworkerの拒否を実PostgreSQLで検証します。失敗保存ができないときに成功を返さないこともApplicationテストで確認します。実店舗での支払・発送成功やShopify workerの接続を示す検証ではありません。

今回の確認では`pnpm check:ci`（通常テスト756件、型・静的検査・ビルド）と、隔離DBの164件が成功しました。新規回帰テストはApplication 2件・DB 12件です。依存監査も既知の脆弱性なし。本番データ・実決済・実店舗設定は使用していません。

戻す場合は、Inboxの取得アダプターとApplicationの戻り値型・処理ループを同時に戻します。DB移行・接続設定・権限追加は不要です。既存のattempts、FAILED状態、通知、監査を削除・リセットしません。旧コードに戻すと、復元不能な通知によるバッチ停止が再発し得ます。
