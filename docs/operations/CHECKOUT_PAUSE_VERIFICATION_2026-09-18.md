# 新規購入停止と既存決済の隔離DB演習

確認日：2026-09-18 JST。対象：#123 / P0-13。実装基準：main `aa84ba7`。自動回帰試験は [native-inventory.database.test.ts](../../src/modules/inventory/infrastructure/native-inventory.database.test.ts) の `settles delayed signed` 2ケース。

## 今回確認した範囲

専用のローカル PostgreSQL 18 に migration と合成データを投入し、既存の購入準備・受付制御・署名検証・暗号化Inbox・ワーカー・注文確定・在庫アダプターを接続した。Stripe SDKのテスト署名を使用し、実Stripe API・実顧客・既存稼働DBには接続していない。CIは既存のPostgreSQL 16サービスで同じ試験を実行する。

| 場面 | 確認する結果 |
| --- | --- |
| 受付を開始後に停止 | 新規購入準備とSession開始を拒否。新規行・在庫予約を作らず、外部Sessionの作成・取得もしない |
| 48時間遅れの通知 | イベント発生時刻は古く、配送署名は新しい通知を受理。署名検証を緩めない |
| 改ざんされた通知 | 同じ署名で本文を変更すると拒否。Inboxを作らず在庫を保持 |
| 既発行Sessionの支払済み通知 | 停止中でもInboxから処理し、注文・決済・発送レコードを各1件作成して在庫を1回だけ消費 |
| Session作成結果が未保存 | ローカル期限経過だけでは在庫を解放せず、署名検証済みの期限切れ通知で1回だけ解放。注文・決済・発送は作らない |
| 重複通知 | 同一イベントの同時3配送は1件だけ保存。処理後の再送、同一Sessionの別イベントIDでも注文・在庫を重複更新しない |
| 再開 | 停止中に拒否された同じ要求IDを再利用でき、繰り返しても予約は1回だけ |

アプリケーションの受付コールバックだけを試験中に切り替える。環境変数の配布やHTTP経路を含む実配備演習とは区別する。本番composition-rootについては既存の [受付停止統合試験](../../src/shared/infrastructure/checkout-intake.integration.test.ts) が、`true` / `false` / 不正値で新規受付を拒否し、既存処理のサービスを構成できることを別途検証する。

## 実施結果と残る確認

- ローカル：対象の在庫DB試験21件成功（今回追加2件）。DB全体284件・通常1,431件・型/Lint/静的検査・ビルド成功。通常実行時のDB/外部試験285件はskipであり、DB284件は専用DB指定で別途実行した。PRのCI結果は対象PRに記録する。
- migration・本番コード・依存パッケージの変更なし。戻す場合は追加試験と文書のみを取り消せばよく、DB復元は不要。
- 2026-09-18のGitHub Environments一覧に `stripe-test` はない。これは他の設定先やStripeアカウント自体の不存在を意味しない。
- #120 の隔離Stripe接続と #115 の権限・担当者確認後、実配備の全インスタンスへ停止設定を反映し、新規HTTP要求の拒否、既発行URLの決済、実署名通知、照合ワーカー、再開を確認する。配備SHA・設定反映時刻・匿名化した結果を証跡として残す。
- 結果不明Sessionの実Stripe照合、分散配備での反映遅延、実際のHTTP再送、Google認証から本人注文履歴までの経路は未確認。#123はこれらの演習完了まで閉じない。

## 停止・再開の境界

`BLOOMBOX_CHECKOUT_INTAKE_ENABLED` は配備単位の受付制御であり、瞬時の分散停止や発行済みSessionの取消ではない。既にStripeへ送った要求は完了し得るため、戻ってきたSessionを保存し、Webhook・照合・復旧処理を継続する。

現在の本番販売はADR 0009の別のコード上の制御でも停止している。フラグを `true` に戻すだけでは販売を開始できない。今回の試験でこの制御は変更しない。承認済みの販売可能な配備で実施する緊急停止・復旧手順は [STRIPE.md](STRIPE.md#emergency-controls) を参照。
