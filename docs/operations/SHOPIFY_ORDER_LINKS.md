# Shopify注文と購入試行の関連付け

2026-09-11時点。Checkoutが所有する不変の関連付けを、内部ワークフロー`AssociateShopifyOrder`に実装しました。`ReadShopifyReference`で正式データを取得してから、Checkoutの公開契約`ShopifyOrderLinker`を呼びます。PaymentがCheckoutのテーブルを直接書き換える構成にはしません。

注文・入金・返金・配送の状態反映、購入者アカウントの認証、公開購入経路、Inbox消費ワーカーへの接続はこの段階では行いません。関連付け成功は「この注文が保存済みの購入試行のカートから作成された」という内部記録です。入金済みや発送可能、閲覧者が購入者本人であることを意味しません。

## 関連付けの根拠

Shopify Admin GraphQL API `2026-07`の`Order.cartToken`は、その注文を作ったカートのトークンです。通知本文の属性やブラウザ入力ではなく、設定済み店舗の認証で取得した正式な値を使います。[公式追加仕様](https://shopify.dev/changelog/new-field-carttoken-added-to-the-order-graphql-admin-api)。

Storefrontから得て暗号化保存した`gid://shopify/Cart/<token>?key=<secret>`から、カート部分のトークンをそのまま取り出します。Base64やパーセント表記を復号せず、大文字小文字・空白を正規化しません。形式を推測して候補を増やす代替照合もしません。API上の表現が一致しなければ安全に保留し、実店舗の証跡を確認します。[公式Cart ID仕様](https://shopify.dev/docs/storefronts/headless/building-with-the-storefront-api/cart/manage)、[トークン形式に関する注意](https://shopify.dev/changelog/changes-to-cart-token-format-for-ajax-and-storefront-graphql-cart-apis)。

外部要求の結果を永続化する際、トークンのSHA-256を`shopify_checkout_attempts.cart_token_digest`へ保存します。店舗とダイジェストの一意制約で、同じカートが別の購入試行に使われることを拒否します。秘密の`key`と生トークンは検索列・ログ・Outbox・監査へ書きません。全カートIDは従来どおり暗号化保存します。ダイジェストも内部の識別情報として扱います。

## 受け入れ条件と原子性

- 認証済み取得結果の店舗、カートトークン、API版が、READYの保存済みShopify試行と一致する。
- 購入準備がShopifyに固定され、CHECKOUT_CREATEDまたはCONVERTEDである。
- 明細が1件で、variant ID、注文数量、作成時単価、JPY通貨が購入時スナップショットと一致する。欠落・追加商品・変更・不正値は保留する。
- 購入準備に別注文が関連付いておらず、同じ店舗・注文が別の購入準備にも関連付いていない。

購入準備の行ロックを試行完了処理と共有し、関連付け・監査・Outboxを1つのDBトランザクションで保存します。外部API呼び出しはトランザクションの前です。同じ関連付けの再実行では既存結果を返し、監査やOutboxを増やしません。途中の保存エラーでは全体を戻し、次の再実行を受け入れます。リンクはDBでもUPDATE/DELETE禁止です。

Order/Payment/Fulfillmentのレコードや状態を作成・更新しません。税・送料・割引・受取人・最終合計の検証と支払い状態判断は、次の注文反映で別途必要です。単価の一致だけで決済内容全体を受け入れるものではありません。返金通知も正式APIで得た関連注文に対して同じ照合を通します。

## 移行と権限

`0006_shopify_order_links.sql`を前進適用し、`database/roles.sql`を再適用します。既存の0001〜0005は変更しません。新しい環境変数・依存パッケージはありません。

Workerはリンク表のSELECT/INSERTだけを持ち、カート認証情報のUPDATE権限は追加しません。関連付けはサーバー内の検証済みAPI結果からだけ呼ぶ契約です。ブラウザや通知の任意フィールドをこの書込ポートへ直接渡す公開経路を作らないでください。

移行前のREADY行は、暗号化カートからSQLだけではダイジェストを計算できないためNULLのまま保持します。新コードで保存済みカートを再取得・照合して購入手続きを再開したとき、同じ認証情報であることを確認して索引を補完します。補完前の行を属性や全件探索で代替照合しません。カートを再取得できない既存行は保留し、別途、管理者用の検証・索引補完手順を完成させる必要があります。新規カートの重複作成で解消しません。

本番公開前に、隔離店舗のStorefrontカートとAdmin注文のトークン表現一致、注文編集・返金・削除済み商品、遅延決済を確認します。現在の自動テストは合成APIデータと隔離DBによる証跡で、実店舗購入の証跡ではありません。

## ロールバックと残件

このワークフローは公開API・定期処理・Inbox消費へ接続していません。アプリ差分を戻す場合も0006、既存リンク、暗号鍵、購入試行を保持します。古いアプリが作った新しいREADY行は索引がNULLになるため、再導入時に補完が必要です。不変リンクの訂正は通常更新で行わず、正式データと影響を確認した専用の前進修正として扱います。

決済状態の照合・原子的な保存と監査/Outboxを内部処理に実装しました（[仕様](SHOPIFY_PAYMENT_EVIDENCE.md)）。残件は最終金額・配送/ギフトを検証した注文受け入れ、状態表示、照合不能時の運用、在庫/配送、未着通知の再照合、保持期限です。Inboxは関連付けできただけで処理済みにしません。本番公開判定は引き続き無効です。

## 検証

通常テストでトークンの不透明な比較、署名済み通知→正式API取得→関連付け呼び出し、偽の通知内トークンの不使用、取得・書込失敗の伝播を確認します。実PostgreSQLでは6マイグレーションの繰返し適用、同時実行の一意性、別注文/別購入への再利用拒否、商品不一致、旧行の保留/補完、不変制約、Worker最小権限、Outbox失敗時の全体ロールバックを検証します。
