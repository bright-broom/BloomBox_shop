# 商品画像の登録・配信（Issue #134 / P0-24）

## 採用した構成

2026-09-17：画像の実体は既存の `public/images/products/` に保管し、アプリと同じ配備で公開する。追加の外部ストレージ・契約・アップロードAPIは増やさない。`content/product-images.json` を配備画像の台帳とし、商品登録/編集、PostgreSQLの商品読取、プレビューカタログ、Next画像最適化の許可をそろえる。管理フォームは台帳の候補を表示し、入力欄に説明を関連付ける。既存フォームと標準HTMLの datalist を再利用し、新しいUI依存はない。

画像ファイルと台帳の追加はリポジトリのPRレビュー・配備権限、商品への紐付けは既存のGoogle運営者認証＋期限付き商品管理権限＋専用DB接続で管理する。商品編集者にファイル配置・任意URL配信の権限を与えない。すべて公開用の素材のみ扱う。個人情報・秘密情報・未許諾素材を保管しない。

## 正式素材を追加する手順

1. 商品責任者がM/Lそれぞれの実物写真・許諾・実商品との対応を確認する。位置情報等の不要なEXIFは配置前に除去する。
2. `public/images/products/` に英小文字・数字・ハイフンのファイル名でPNG/JPEG/WebPを追加する。SVG、サブディレクトリ、任意のパスは対象外。更新時は新しいファイル名にし、キャッシュと戻し先を明確にする。
3. `content/product-images.json` に `src`（`/images/products/...`）、`label`（管理者が識別できる説明）、`kind`（`photograph` または `concept`）を追加する。`photograph` は実物を確認した写真に限定する。kindは事実の宣言であり、自動で許諾や品質を証明するものではない。
4. 画像台帳テストでファイルの存在・形式と拡張子・許可設定を確認し、PRレビューを経て配備する。配備後のURLと最適化画像が表示できることを確認してから商品へ紐付ける。
5. `/operations/catalog` で画像候補を選び、商品の画像説明を記入して保存する。公開/停止、バージョン競合、監査履歴は既存のまま。TOPギャラリー/レビューの写真にも使う場合は同じ台帳の `photograph` を指定し、別途既存の公開承認を満たす。
6. M/Lの商品ページ、一覧、カート、管理画面を確認する。正式カタログ・実在庫・販売開始の承認はこの画像配備と別に行う。

## 制限とセキュリティ

- 完全一致の台帳パスのみを受け付け、クエリ・フラグメント・パストラバーサル・未登録パス・SVGを拒否する。Nextの localPatterns も同じ台帳から生成する。
- 互換用のUnsplash HTTPS画像は引き続き使用できる。ホスト偽装、資格情報、追加ポート、フラグメントを拒否する。
- Next画像最適化では外部リダイレクトを無効化し、許可ホストから別ホストへの転送で制限が迂回されないようにする。既存ホストが転送を始めた場合も、許可先を広げず実体のURLを確認する。
- 正式な物撮りはまだ提供されていない。現在の台帳は青いパッケージ案1枚（M/L共用、`concept`）のみ。案画像を正式商品写真として登録済みとは報告しない。素材受領・M/L正式登録・公開環境での実接続確認が残る。

## 検証と復旧

2026-09-17：`pnpm check:static`、通常テスト1,241件、`pnpm build` が成功。今回専用の隔離PostgreSQLで商品管理DBテスト11件が成功（権限付きの画像保存→公開→在庫→顧客カタログ読取、監査、再送、不正パス拒否）。既存の共有DBは使用していない。ローカルproduction buildのHTTP確認でM/Lページ・元PNG・640px最適化画像は200、未登録画像と `/api/health` を画像として取得する要求は400。実Googleログイン・公開Vercelへの配備・正式写真の目視は未実施。

関連試験は画像台帳の正常系/不正参照、管理保存スキーマ、フォームの候補・説明、プレビューカタログ、TOPの案画像拒否を対象とする。画像の署名確認は基本形式を確認するもので、権利や撮影内容を検証するものではない。

誤った紐付けは商品管理画面から元の画像に訂正し、変更履歴を保持する。配備を戻す前にDBが参照する画像が戻し先にも存在するか確認する。参照中の画像を台帳・publicから先に削除すると安全側に読取エラーとなるため、旧画像は利用終了まで残す。販売停止ゲート・DBスキーマ・認証設定の変更はない。
