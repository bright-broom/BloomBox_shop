# Shopify注文の確定保存

2026-09-11時点。`PostgresShopifyOrderAcceptor`は、承認済みの販売条件と検証済みのShopify情報から、Order所有の注文を一度だけ保存する内部Adapterです。初期設定は`approval: PENDING`。公開経路・Inbox worker・`ReconcileShopifyPayment`には未接続で、本番決済Gateも無効のままです。

## 受け入れ条件

呼出元はブラウザーや通知内の価格・配送先を渡してはいけません。認証済みAdmin APIから得た同一注文の価格・配送先・更新時刻と、保存済み決済版を渡す内部コマンドです。JSONの構造検証は出所の認証を代替しません。現在の配送先Adapterは秘匿化した判定だけを返すため、完全な配送先（建物名・電話を含む）の安全な受け渡しは別途接続が必要です。

- 明示的に承認された配送地域、商品別送料、税込/税別、test/live区分、注文個人情報の保持日数が必要です。テストの東京都・税込・90日は合成条件で、事業上の承認ではありません。
- 注文金額を再照合し、商品/送料の内税・外税配賦を保持します。紹介特典の資格・使用済み管理が未接続なので、商品/送料の割引が1円でもあれば保留します。紹介特典の最低商品小計5,500円は変更しません。
- 保存済みの購入準備、購入試行、店舗、注文の関連付けがすべて一致することを確認します。商品variant・数量・購入時単価・JPY・承認された送料も照合します。
- 最新決済版・注文更新時刻、テスト区分、全額入金、取消なし、返金なし、処理中取引なしを確認します。決済の観測後に返金が先に保存された場合、古い版で注文を確定しません。
- 購入準備は`CHECKOUT_CREATED`、必要な個人情報は未削除・保持期限内であることが必要です。保存直前の時刻で東京時間の配送受付期間も再確認します。購入準備のTTLを事業者の支払期限として扱いません。

## 保存・競合・個人情報

購入準備を最初にロックし、次に決済記録を共有ロックします。他モジュールの記録は参照だけで、更新しません。外部APIをトランザクション内で呼びません。

1トランザクションで`orders`（CONFIRMED）、`order_items`、`order_gift_snapshots`、変更不能な`shopify_order_acceptances`、状態遷移、監査、`order.shopify.accepted` Outboxを保存します。どれかが失敗するとすべて戻ります。同時実行は購入準備のロックと一意制約で直列化され、再試行は既存注文IDを返します。後から返金されても、受け入れ時の注文・価格証跡を上書きしません。返金後の状態処理は別コマンドが必要です。

配送先・贈り先の名前・ギフト本文は注文IDに結び付けたAADで暗号化します。購入準備の暗号文をそのまま流用しません。購入者ID・受取人IDを氏名から推測して作成せず、未関連のguestとして保持します。監査・Outbox・結果には氏名、住所、電話、本文を含めません。例外も固定メッセージに変換します。

保持期限は注文スナップショットに保存しますが、確定注文の削除処理・バックアップ中の扱い・本人確認・閲覧権限は未完了です。期限列だけで削除対応済みとは扱いません。

## マイグレーションと復旧

`0008_shopify_order_acceptance.sql`を既存移行の後に適用し、`database/roles.sql`を反映します。新しい`order_items.included_tax_minor`はnullableです。既存明細の不明な内税を0に置換せず、既存Stripe書込との互換性を維持します。新Adapterは検証した内税額（税別なら0）を明示的に保存します。

Order所有の受け入れ証跡には注文・購入準備の一意制約、店舗を含む既存関連付けへの外部キー、UPDATE/DELETE拒否トリガーを設けます。worker権限はSELECT/INSERTのみです。依存追加・環境変数追加はありません。

公開前のロールバックは未接続Adapterの利用を停止してコードを戻します。適用済み移行・確定注文・金額証跡を削除しません。永続データの修正は新しい前進移行または所有モジュールの監査付きコマンドで行います。

## 検証と次の接続

隔離PostgreSQLで全8移行の再実行、6並列の作成/再試行、税込/税別の注文・明細・送料税、旧書込のNULL互換、暗号化とAAD、保存失敗時の全体ロールバック、権限、証跡変更拒否を確認します。返金トランザクションのロック待機中に決済版が進む競合も再現し、確定を保留することを確認します。

次は、完全な配送先を取得する内部Provider境界と本コマンドの接続、Checkout所有のCONVERTED遷移、Payment/返金の注文関連付け、Fulfillmentの承認、Outbox消費、注文の安全な参照を実装します。事業条件・実店舗接続・個人情報保持運用・在庫方針・購入者の認可を揃え、隔離店舗E2Eを完了するまで販売開始しません。今回のDBテストは実店舗での支払・発送成功の証拠ではありません。
