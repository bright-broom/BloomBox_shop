# Shopify注文の確定保存

2026-09-11時点。`PostgresShopifyOrderAcceptor`は、承認済みの販売条件と検証済みのShopify情報から、Order所有の注文を一度だけ保存する内部Adapterです。初期設定は`approval: PENDING`。`ReconcileShopifyPayment`から任意注入の`ShopifyOrderAcceptanceGateway`を通じて接続しました。公開経路・Inbox workerには未接続で、本番決済Gateも無効のままです。

## 受け入れ条件

呼出元はブラウザーや通知内の価格・配送先を渡してはいけません。認証済みAdmin APIから得た同一注文の価格・配送先・更新時刻と、保存済み決済版を渡す内部コマンドです。JSONの構造検証は出所の認証を代替しません。`ShopifyAdminOrderAcceptor`が建物名・電話を含む配送先を最後に再取得し、Orderコマンドへ渡します。平文の受け渡しはInfrastructure内に限り、Applicationの結果には含めません。

- 明示的に承認された配送地域、商品別送料、税込/税別、test/live区分、注文個人情報の保持日数が必要です。テストの東京都・税込・90日は合成条件で、事業上の承認ではありません。
- 注文金額を再照合し、商品/送料の内税・外税配賦を保持します。紹介特典の資格・使用済み管理が未接続なので、商品/送料の割引が1円でもあれば保留します。紹介特典の最低商品小計5,500円は変更しません。
- 保存済みの購入準備、購入試行、店舗、注文の関連付けがすべて一致することを確認します。商品variant・数量・購入時単価・JPY・承認された送料も照合します。
- 最新決済版・注文更新時刻、テスト区分、全額入金、取消なし、返金なし、処理中取引なしを確認します。決済の観測後に返金が先に保存された場合、古い版で注文を確定しません。
- 購入準備は`CHECKOUT_CREATED`、必要な個人情報は未削除・保持期限内であることが必要です。保存直前の時刻で東京時間の配送受付期間も再確認します。購入準備のTTLを事業者の支払期限として扱いません。


## 決済確認からの接続

内部フローは正式な注文照会→関連付け→決済観測の保存→金額照合→配送期限→配送先の構造/地域確認→期限の再確認→注文確定です。最後の注文確定では、承認済み条件の場合だけ追加の保護情報照会を行い、`address2`と`phone`を取得します。初回の構造確認と最後の完全な住所取得は別照会で、通常は注文照会を含む計3リクエストです。請求先、メール、位置情報は取得しません。[Shopify MailingAddressの正式フィールド](https://shopify.dev/docs/api/admin-graphql/2026-07/objects/MailingAddress)を使用し、追加項目の明示的nullは保持、欠落/上限超過/権限エラーは失敗として扱います。

最後の照会も店舗・注文ID・test区分・API版を照合します。元の注文照会と更新日時が異なる場合や取消済みなら`ORDER_CHANGED`、配送不要なら`SHIPPING_NOT_REQUIRED`で保留します。書込時には既存AdapterがDBロック内で最新決済版・期限・販売条件を再確認します。別々の外部API照会を原子的な読取とは扱いません。最終照会後の事業者側更新は後続通知・再照合で処理し、発送前にも別途承認が必要です。

返却値のトップレベル`outcome`は決済観測の保存結果です。追加の`acceptance.outcome`が注文のCREATED/DUPLICATE/HELDを表し、2つを混同しません。Gateway未注入なら`NOT_CONFIGURED`、前提条件不成立なら`PREREQUISITES_UNRESOLVED`、販売条件未承認なら`TERMS_NOT_APPROVED`で保留します。GatewayとOrder Adapterへ同じ承認済み方針を注入することが必要です。

保護情報照会や注文保存が失敗しても、先に確定した決済記録を削除しません。例外を呼出元へ伝播し、再試行で決済記録を重複保存せず注文作成へ進みます。注文確定の成功もInbox全体の処理完了ではありません。Checkout変換・Payment/返金・Fulfillmentの処理が未完了なので、受付イベントを処理済みにする接続は行いません。

## 保存・競合・個人情報

購入準備を最初にロックし、次に決済記録を共有ロックします。他モジュールの記録は参照だけで、更新しません。外部APIをトランザクション内で呼びません。

1トランザクションで`orders`（CONFIRMED）、`order_items`、`order_gift_snapshots`、変更不能な`shopify_order_acceptances`、状態遷移、監査、`order.shopify.accepted` Outboxを保存します。どれかが失敗するとすべて戻ります。同時実行は購入準備のロックと一意制約で直列化され、再試行は既存注文IDを返します。後から返金されても、受け入れ時の注文・価格証跡を上書きしません。返金後の状態処理は別コマンドが必要です。

配送先・贈り先の名前・ギフト本文は注文IDに結び付けたAADで暗号化します。購入準備の暗号文をそのまま流用しません。購入者ID・受取人IDを氏名から推測して作成せず、未関連のguestとして保持します。監査・Outbox・結果には氏名、住所、電話、本文を含めません。例外も固定メッセージに変換します。

保持期限は注文スナップショットに保存しますが、確定注文の削除処理・バックアップ中の扱い・本人確認・閲覧権限は未完了です。期限列だけで削除対応済みとは扱いません。

## マイグレーションと復旧

`0008_shopify_order_acceptance.sql`を既存移行の後に適用し、`database/roles.sql`を反映します。新しい`order_items.included_tax_minor`はnullableです。既存明細の不明な内税を0に置換せず、既存Stripe書込との互換性を維持します。新Adapterは検証した内税額（税別なら0）を明示的に保存します。

Order所有の受け入れ証跡には注文・購入準備の一意制約、店舗を含む既存関連付けへの外部キー、UPDATE/DELETE拒否トリガーを設けます。worker権限はSELECT/INSERTのみです。依存追加・環境変数追加はありません。

公開前のロールバックはGatewayの注入を外して決済照合のみへ戻します。適用済み移行・確定注文・金額証跡を削除しません。永続データの修正は新しい前進移行または所有モジュールの監査付きコマンドで行います。

## 検証と次の接続

隔離PostgreSQLで全8移行の再実行、6並列の作成/再試行、税込/税別の注文・明細・送料税、旧書込のNULL互換、暗号化とAAD、保存失敗時の全体ロールバック、権限、証跡変更拒否を確認します。返金トランザクションのロック待機中に決済版が進む競合も再現し、確定を保留することを確認します。

追加の通し検証では、模擬Admin API→関連付け→決済保存→保護情報取得→実DB注文保存を実行します。取得失敗後に入金記録が残ること、再試行と6並列で注文が1件になること、建物名・電話が暗号化されること、更新時刻差・最後の住所取得中の配送期限越えによる保留を確認しました。通常テスト486件、DBテスト46件と全体チェックが成功しています。実店舗の権限承認や通信の成功を示すものではありません。

次は、Checkout所有のCONVERTED遷移、Payment/返金の注文関連付け、Fulfillmentの承認、Outbox消費、注文の安全な参照を実装します。事業条件・実店舗接続・個人情報保持運用・在庫方針・購入者の認可を揃え、隔離店舗E2Eを完了するまで販売開始しません。今回のDBテストは実店舗での支払・発送成功の証拠ではありません。
