# 承認操作の送信制限

2026-09-12。[承認フォーム](OPERATOR_APPROVAL_FORM.md)の送信に、担当者ごとの直近60秒・最大10回の制限を追加しました。事業方針は PENDING のままです。実担当者への権限付与や本番有効化は行いません。

## 対象と振る舞い

[権限失効の管理画面](OPERATOR_PERMISSION_MANAGEMENT.md)も同じ枠を利用します。サーバーで検証した担当者 UUID をキーにします。ブラウザーからキーを選べず、別タブ・再ログイン・別サーバー・店舗や test/live 区分の変更でも同じ担当者の枠を共有します。別担当者は別枠です。許容量は Fulfillment の `APPROVAL_SUBMISSION_POLICY` に集約しています。DBも配列長を10件に制限するため、上限を増やす場合は新しい前進移行が必要です。

Origin、現在の認証と担当者対応付け、フォームの構造、事業方針の検証後、暗号化された確認情報の検証と承認トランザクションの前に枠を消費します。同じ確認情報の再送、改ざんされた確認情報、在庫期限などによる承認失敗も枠を使います。拒否された追加送信は枠の期限を延長しません。匿名・不正 Origin・構造不正・事業方針 PENDING ではこの保存処理に到達しません。

制限は承認・認可の代わりにはなりません。枠を取得しても既存コマンドは店舗権限・セッション・確認版・入金・在庫を再検証します。冪等キーを変更せず、同じ画面で後から再送できます。在庫根拠は30秒で古くなるため、待機後には再照合と新しい版の確認が必要になる場合があります。承認履歴と保存済み根拠を確認し、成功を推測して発送しないでください。

## 永続化と障害

移行0015は `fulfillment_approval_submission_limits` を追加します。担当者 UUID ごとに1行、最大10個の送信時刻だけを保持し、次の許可時に古い時刻を置き換えます。トークン・住所・氏名・IP・ギフト本文は保存しません。行数はマッピングされた担当者数に応じて増え、定期削除は行いません。無効な担当者行の削除が必要な場合は、担当者対応付けとアクセスを失効し、未処理要求がないことを確認してDB管理者が実施します。稼働中の削除は制限をリセットするため行いません。

短い独立トランザクションで行ロックを取得し、その後のDB時刻で直近60秒を判定します。アプリの時計や固定の分境界に依存しません。DB時計が巻き戻った場合は未来の時刻も数えて拒否側に倒します。[PostgreSQLの行ロック](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)と [clock_timestamp](https://www.postgresql.org/docs/current/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)を使用します。

枠の消費は承認の成否と別に確定します。後続の処理失敗で枠を返しません。通信が切れて消費結果が不明の場合も承認に進まず、次の送信では再度枠を確認します。ロック待ちは1秒、各SQL実行は2秒で打ち切り、DB障害・移行不足・権限不足・不正な保存状態では UNAVAILABLE として停止します。メモリーへの切替や無制限のフォールバックはありません。

これは認証済み担当者の承認処理を抑制する機能です。HTTP到達前の大量通信、Googleログイン、一覧や詳細の読み取りを制限するものではありません。公開運用では入口側の通信量対策と認証側の対策も別途評価してください。

## 適用・戻し方

1. DB所有者の資格情報で前進移行0015を適用します。既存14移行の内容は変更していません。
2. `database/roles.sql` を再適用します。専用の `bloombox_fulfillment_approver` に新表の SELECT/INSERT と時刻列の UPDATE だけを付与します。担当者キーの変更・DELETE、および一般アプリ・workerによる書き込みは許可しません。
3. 新版へ切り替え、旧版の承認送信経路への流入を止めてから有効化を評価します。新コードは旧DBで拒否しますが、旧コードにはこの制限がありません。事業方針 PENDING は変更しません。

環境変数や依存の追加はありません。戻す際は承認操作を停止した状態で旧版へ切り替え、追加表・移行・承認履歴は保持します。制限を外したまま承認操作を再開しないでください。実 Google 接続、監査付き権限管理、事業条件の承認、実店舗の承認成功E2Eは残件です。

## 検証

通常660件、隔離PostgreSQL97件、型・Lint・静的検査・本番ビルドが成功しました。本番依存監査では既知の脆弱性はありません。移行の再適用、別接続からの24並列送信（許可10・拒否14）、別担当者の分離、期限経過による回復、未認証／期限切れ、保存状態の異常、専用ロール、ロック待ちの打切りと待機後のセッション再検証を含みます。承認・監査・Outboxが制限処理だけでは増えないことも検証します。

アプリ側は制限拒否・DB障害で承認アダプターを呼ばず、再送も同じ本人で毎回枠を消費すること、画面が元の確認情報を保持して待機案内を通知することを検証します。事業方針 PENDING のため、実 Google と実店舗を使った承認成功のブラウザーE2Eは今回の証跡に含みません。
