# Shopify通知の滞留診断

Shopifyの通知受付は現在capture-onlyで、[テスト注文限定worker](SHOPIFY_INBOX_WORKER.md)も初期停止です。保存後の状態を追跡するため、未処理件数・待機時間・再試行・失敗・保持期限を確認するオフライン診断を追加しました。通知本文を復号せず、注文・決済・発送やInboxの状態も変更しません。

## 接続と実行

1. 移行0019を適用し、`database/roles.sql`を再適用します。移行は未完了の通知だけを店舗・受信時刻順に読むインデックスを追加します。通常のトランザクション内CREATE INDEXなので、通知が多い環境では書込みを短時間止める可能性があり、運用時間を調整します。
2. 専用LOGINに`bloombox_inbox_monitor`だけを付与します。これは全店舗の運用メタデータを読む権限です。店舗指定はクエリの絞り込みであり、担当者の店舗別認可ではありません。店舗別担当者・Webアプリ・既存worker/readonlyロールに付与せず、信頼する運用担当者の接続として管理します。
3. `DATABASE_INBOX_MONITOR_URL`を非公開の実行環境に設定します。既存のDB接続変数へのフォールバックはありません。TLSは`verify-full`、`disable`はlocalhost/127.0.0.1の隔離DBだけで使用できます。URLのクエリ文字列によるSSL設定の上書きは拒否します。復号鍵やShopify APIキーは不要です。
4. Node 24で実行します。引数は対象店舗と待機時間の警告しきい値（秒、1〜2,592,000）です。次の900秒は操作例であり、確定した運用SLAではありません。

```sh
node scripts/inspect-shopify-inbox.mjs example.myshopify.com 900
```

JSONには対象店舗・DBの確認時刻・各件数・最古のPENDING待機秒数・理由コードだけを出します。イベントID、注文ID、エラー本文、worker名、通知本文、復号鍵、住所などは出しません。専用ロールの列権限も本文・外部参照・エラー列と他のcommerceテーブルを拒否します。接続設定・権限・SQL・タイムアウトの失敗は固定エラーになり、接続先やSQLパラメータを出しません。

集計対象は指定店舗のSHOPIFY通知全体です。通知本文を読まないためtest/liveは分類しません。未登録・誤指定の店舗もEMPTYになるので、対象店舗とDB接続先は運用側で照合します。

## 判定の読み方

| 終了コード | 判定 | 意味 |
| --- | --- | --- |
| 0 | EMPTY | 対象店舗に未完了通知がない。通知が届いていることや設定の正しさは保証しない |
| 0 | WITHIN_LIMITS | 対象範囲に通知はあるが、今回のしきい値・異常条件に該当しない |
| 2 | ATTENTION | 待機時間超過、失敗、停止した処理、保持期限超過、本文欠落、未来時刻、走査上限のいずれか |
| 1 | 診断不能 | 引数・設定・権限・接続・DB障害。正常として扱わない |

`pending = ready + scheduled`です。`retrying`はPENDINGのうち処理失敗回数が1回以上の部分集合なので、件数合計に足しません。`stalled`はPROCESSINGのうちロック時刻なし、またはworkerと共通の5分の回復期限に達した部分集合です。未来の受信・ロック時刻も要確認になります。時間判定は一つのSQLのDB時刻を使い、ローカル端末の時計に依存しません。PENDINGの待機時間は最初の受信から測り、再試行予約によって長期滞留を隠しません。

古い受信順で最大10,001件だけを集計します。10,000件以内は`coverage: COMPLETE`、上限検出の1件に達したら`LOWER_BOUND`と`SCAN_LIMIT_REACHED`を返します。LOWER_BOUNDでは各件数は実際の件数の下限で、未走査範囲の異常は不明です。必ずATTENTIONとなり、件数ゼロの分類も全件ゼロとは解釈しません。確認中の更新は次回の結果に反映されます。

READ ONLYトランザクションを使い、SQLは2秒、ロック待ちは1秒、接続は5秒で打ち切ります。完了済み履歴を走査しない部分インデックスを利用可能にし、大量履歴による負荷を抑えます。読取の反復は通知のclaim・再試行日時・attempts・監査・Outboxに影響しません。

## 要確認時の対応と限界

capture-only環境ではPENDINGが溜まるのは現在の仕様です。限定した隔離店舗での通知受付検証に使い、長期に受け続ける運用は行いません。警告を消す目的で通知を削除したり、PROCESSEDへ直接書き換えたりしません。

失敗・停止・期限超過がある場合は、通知受付の設定・接続権限・保存期間・後続処理の接続状況を確認します。本文が消えた記録から再処理できるとは限りません。正式APIによる再照合と監査付きの復旧を別途実装する必要があります。

本機能は定期実行・通知送信・Shopify API照会を開始しません。未着通知の検出、workerの実店舗検証、再処理、注文の正常性、本番公開可否は別の検証です。EMPTY/WITHIN_LIMITSを販売開始の根拠にしません。

## 検証と戻し方

設定の検証と隔離PostgreSQLで、店舗/providerの分離、状態別集計、しきい値、再実行の無変更、期限超過、未来時刻、10,000件境界、列権限、実際のロック競合、CLIの終了コードを確認します。画面・外部APIは変更しないため、ブラウザーや実店舗での決済成功をこの検証の証拠とはしません。

今回のローカル確認では`pnpm check:ci`（通常テスト754件、型・静的検査・ビルド）と隔離PostgreSQLの152件が成功しました。新規の診断DBテストは14件、設定テストは11件です。依存監査も既知の脆弱性なし。テスト用DBだけに移行・ロールを適用し、実店舗や本番接続は使用していません。

戻す場合は診断の実行を止め、専用LOGINのロール付与を外します。移行0019のインデックスは残して問題ありません。既存通知・履歴を削除せず、適用済み移行は書き換えません。本番gate、事業条件、capture-only設定は変更していません。

## 最後に記録した保留理由

移行`0021_shopify_inbox_failure_categories.sql`と更新した`database/roles.sql`を先に適用すると、診断結果に`lastFailureCategories`が加わります。DB所有者のビューは既存の運用メタデータに加え、許可した固定コードから作る分類だけを公開します。監視ロールに`last_error_code`本文の読取権限は与えません。未知の値は必ず`UNKNOWN`となり、注文ID・住所・エラー本文を診断へ返しません。

| 分類 | 対応 |
| --- | --- |
| `configuration` | 注文/発送受付の依存設定を確認 |
| `terms` | 税・送料等の受け入れ条件と店舗設定を確認 |
| `payment` | 正式API上の入金・取消・返金状態を確認。入金待ちは自動で入金済みにしない |
| `pricing` | 金額・税額配賦・割引・変更注文を確認 |
| `delivery` | 希望日の期限・配送地域・住所の検証結果を確認 |
| `order` | 古い観測・取消・購入準備の期限/状態を確認 |
| `incomplete` | 旧バージョンの包括的な保留、または特定できない受け入れ保留。詳細な再照合が必要 |
| `unknown` | 未分類の外部/DB障害等。原文は開示せず別途調査 |
| `none` | 失敗コードの記録なし。成功や健全性の証明ではない |

これは対象通知の**最後に記録された失敗**の件数です。現在の注文状態や原因解消を証明せず、再投入直後・処理中には前回の分類が残ります。未処理通知1件につき1分類で、合計は`counts.observed`と一致します。10,000件を超える場合は同じ古い順の観測範囲の下限値です。設定・条件・価格・配送・注文の確認が必要な分類には`COMMERCE_REVIEW_REQUIRED`を返して終了コード2とします。入金待ちだけでは即時警告にせず、既存の時間超過・FAILED等の基準を維持します。

移行やビューの権限が不足する場合は`UNAVAILABLE`で終了し、不完全な集計を正常と報告しません。戻す場合は先に診断コードを旧版へ戻し、必要に応じビューのSELECT権限を外します。追加ビューと履歴・固定コードは残して構いません。再試行回数・処理済み条件・出荷判断は変更しません。
