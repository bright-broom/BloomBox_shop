# 担当者・店舗管理者の権限登録と更新

2026-09-12。DB所有者向けのオフライン運用ツールを追加しました。店舗別の承認権限と、承認権限を失効させる管理者権限を、事前確認してから登録・更新できます。実アカウントや店舗への権限付与は行っていません。

## 権限境界

`scripts/provision-operator-access.mjs` がFulfillment所有の保守Adapterを呼びます。HTTPや管理画面には接続せず、スキーマと対象表の所有者権限を持つDB接続だけを許可します。一般アプリ・worker・readonly・承認用・権限管理用の既存ロールは、事前確認も適用も拒否します。既存ロールの権限拡張や管理者の自動登録はありません。前進移行0018で、この運用の監査記録をDB所有者だけが作成でき、更新・削除できないよう保護します。通常処理の監査追記は維持します。

先に[通常のDB移行手順](../../database/README.md)で0018を適用します。保護トリガーが未適用・無効なら、ツールは事前確認も適用も拒否します。新しいロール付与は不要です。

実行にはNode 24（CIと同じ環境）とインストール済みの依存関係が必要です。サーバーの秘密管理から `DATABASE_OPERATOR_ADMIN_URL` に対象DBの所有者用接続を設定します。他のDB環境変数へのフォールバックはありません。アプリ／worker／Vercel Previewへこの接続を渡しません。

接続は既定で `DATABASE_SSL_MODE=verify-full` を使用し、`disable` はlocalhost／127.0.0.1の隔離検証だけで許可します。接続URLのquery／fragmentは拒否し、TLS設定をURL側で上書きできません。URL、パスワード、メール、Google subjectをコマンド引数・入力ファイル・公開Gitへ含めません。入力ファイルは16KiBまでの単一JSONです。

## 入力と事前確認

まず非公開の運用記録で、実施者、権限を与える対象者、検証済みGoogle subjectと内部担当者UUIDの対応、店舗、付与する役割、期限、理由、環境を確定します。Googleログインの許可・対応付けは[認証設定](GOOGLE_OPERATOR_LOGIN.md)に従い別途行います。管理者権限は承認権限と別であり、同じ人が両方必要なら別の変更として登録します。

次の合成例を参考に、公開リポジトリ外へ権限を限定した入力ファイルを作成します。

```json
{
  "changeId": "00000000-0000-4000-8000-000000000001",
  "database": "bloombox_test",
  "kind": "APPROVER",
  "permissionId": "00000000-0000-4000-8000-000000000002",
  "operatorId": "00000000-0000-4000-8000-000000000003",
  "shop": "example.myshopify.com",
  "expectedVersion": 0,
  "enabled": true,
  "validUntil": "2026-09-30T00:00:00.000Z",
  "reason": "INITIAL_ASSIGNMENT"
}
```

- `changeId`：変更ごとの新しいUUID。非公開の実施記録と監査の対応キーにします。同じ操作の再送では保持します。
- `database`：接続先の実DB名。違うDBへの誤適用を拒否します。同名DBは区別できないため、秘密管理の環境と接続先も確認します。
- `kind`：`APPROVER`（注文参照・発送受付の承認権限）か `PERMISSION_MANAGER`（店舗内の承認権限を失効する管理権限）。他の管理権限には拡張できません。
- `permissionId`／`operatorId`／`shop`：権限登録UUID、内部担当者UUID、Shopify店舗ドメイン。新規登録では新しい登録UUIDを作り、更新では既存の組を保持します。担当者や店舗の付け替えは拒否します。
- `expectedVersion`：新規は0、更新は確認した現在の版。更新は版を1増やすため、既存の承認や管理判断の再送が無効になる場合があります。同じ内容の適用でも新しい変更IDなら版が進みます。
- `enabled`／`validUntil`：明示的な有効性とUTC期限。新規・有効化の期限はDB現在時刻より後とし、更新では作成時刻より後を保ちます。無効化では既存期限を保持できます。
- `reason`：`INITIAL_ASSIGNMENT`、`ROLE_CHANGE`、`ACCESS_RENEWAL`、`SECURITY_RESPONSE`の固定分類。自由記入や実施者の自己申告IDは受け付けません。

事前確認（書き込みなし）:

```sh
node scripts/provision-operator-access.mjs /private/path/request.json
```

`PLAN` の応答に、正規化した入力、現在値 `before`、更新後の予定値 `proposed`、確認用の `planHash` を返します。版が違う場合は停止します。変更対象の現状を読み直し、必要なら入力を修正して再確認します。出力は権限情報なので非公開の実施記録へ保存してください。

## 適用と再送

確認した同じファイルと `planHash` で適用します。`--apply`だけや余分な引数では実行できません。

```sh
node scripts/provision-operator-access.mjs /private/path/request.json --apply=<PLANで返された64文字のハッシュ>
```

`<...>` は説明用です。実行時は山括弧ごと実際のハッシュに置き換えます。ハッシュは入力と確認時点の状態を結び付けるもので、認証情報や権限の代わりではありません。

適用時に所有者権限・DB名・対象の組・現在版・期限を再確認し、確認後の変更や別入力を拒否します。対象のロックを取得してから再確認するため、同時操作でも更新を上書きしません。ロック待ちは1秒、SQL実行は各2秒に制限します。DB接続開始の待機は5秒です。

権限の変更、既存トリガーによる改訂監査、変更ID付きの運用監査を同じトランザクションに保存します。途中失敗や保存中の期限切れでは全て戻します。運用監査は `SYSTEM`／`operator-access-provisioning` で、入力・変更前後・理由・確認ハッシュを記録します。Google本人認証によるOPERATOR監査ではありません。実際の実施者は非公開の変更記録で追跡してください。

`APPLIED` は保存成功、同じ変更ID・入力・ハッシュの再実行は `DUPLICATE` です。再送では版・期限・監査を増やしません。保存結果が不明な場合は、同じファイルとハッシュで再実行してください。変更後に別の更新や失効が入っていた場合は、旧操作を再適用せず `REVIEW_REQUIRED` で停止します。`DUPLICATE` は過去の保存結果の一致であり、現在も期限内であることを保証しません。

`CONFLICT` は変更IDの使い回しや対象の組の不一致、`NOT_AUTHORIZED` は所有者権限不足、`WRONG_DATABASE` はDB名違い、`INVALID_REQUEST` は入力不正、`UNAVAILABLE` は接続・保存・タイムアウトなどの失敗です。生のDBエラーや入力内容を出力しません。原因確認の際も秘密値や個人情報を公開ログへ貼り付けないでください。

## 復旧と残件

誤った登録は、新しい変更IDと最新の版で `enabled=false` にします。誤った期限や失効を復旧する場合も、新しい変更として事前確認・適用します。権限行や監査の削除、版の巻き戻し、別の操作に既存の変更IDを再利用しません。通常の承認権限の失効には[権限管理画面](OPERATOR_PERMISSION_MANAGEMENT.md)も利用できます。

このツールを戻すときは運用入口を停止し、登録済みの権限と監査を保持します。移行0018と監査保護は残します。コードを戻しても付与済み権限は自動失効しません。必要な無効化を先に別変更で実施し、所有者資格情報の利用範囲を閉じます。実行には強いDB資格情報が必要であり、DB所有者による直接SQLや監査改変そのものを防止する機能ではありません。

実管理者の指定、実Google接続、専用ロールの実ログイン資格情報、実店舗での確認は残件です。事業方針PENDINGと本番Gateは変更しません。発送指示・支払い・注文変更・外部通知は発生しません。
