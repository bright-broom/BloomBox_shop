# ADR 0010: 自作カタログの在庫予約

- Status: Accepted implementation direction, 2026-09-13. 本番販売は引き続き停止。
- Extends: ADR 0009、ADR 0002。

## 判断

Inventoryは商品SKUごとの販売可能な箱数、予約、確定・解放の履歴を所有する。花材ロット、配送日別の製作枠、返品の再販売可否は今回の数量と混同せず、別途運用を決める。実在庫の初期値は推測しない。

購入準備・商品明細・在庫予約・通知予定を単一トランザクションで保存する。商品行の予約数は条件付き更新で増やし、手持ち数を超えない。予約の識別子は購入準備IDとし、同じ操作で重複確保しない。

予約の状態はHELD→COMMITTEDまたはHELD→RELEASED。確定は販売可能な手持ち数と予約数を両方減らす。解放は予約数だけを減らす。状態と数量変更と履歴を同時に確定し、終端状態から逆方向へ移動しない。

## 解放の根拠

外部決済先を選択する前の購入取消、または未着手の期限切れで解放する。決済先を選択した後は、通信断で結果不明でも予約を保持する。ブラウザーの戻る操作・キャンセルURL・ローカルの経過時間を根拠に解放しない。Stripeの署名検証済み期限切れ・非同期決済失敗イベントから、保存済み決済IDと一致する場合に解放する。

2026-09-14追記：決済先を選択した後、決済作成の応答が失われて決済IDを保存できなかった取引は、同じ購入準備IDを持つStripeの署名検証済み期限切れイベントを根拠に解放する。決済URLが顧客に届いていないため、このSessionを終わらせるのは期限切れだけであり、署名済みの期限切れはStripe側の権威ある証拠である。決済IDの列は空のまま期限切れにし、監査には通常の期限切れと区別した記録を残す。決済完了・非同期決済失敗のイベントは、引き続き保存済み決済IDとの一致を必須とする。決済作成の要求自体がStripeに届かなかった取引には、期限切れイベントがない。

2026-09-14追記：このため、決済先を選択済みで決済IDのない取引は、期限の15分後からStripe側の照合で扱う。保護されたコマースワーカーは、イベントの取り込みと処理を終えた後、対象の取引ごとに、購入準備の作成から期限までに作られたStripeのCheckout Sessionを一覧し、同じ購入準備IDのSessionを探す。該当するSessionがない、または該当するSessionがすべて期限切れ・未払いの場合だけ、予約を解放して期限切れにする。完了・支払処理中・有効など、それ以外のSessionが1つでもあれば解放せず、要確認として監査に一度だけ記録し、ワーカーの実行を失敗させて担当者に知らせる。期限後は決済URLを取得し直せず、作成済みのSessionも同じ期限で失効するため、この照合結果はタイマーではなくStripe側の証拠として扱う。Stripeへの問い合わせはDBトランザクションの外で行い、解放の直前に購入準備を行ロックで再確認する。Checkout Sessionの読み取りはアプリケーション用制限キーの既存の権限を使い、イベント用キーの権限は広げない。

入金確認時は同じ注文保存トランザクションで在庫を確定する。確定後に遅れて届く期限切れ通知は何も解放しない。解放後の矛盾した入金通知は自動で再確保せず、Inboxに失敗を保持して照合する。返金だけでは在庫を戻さない。

## 境界と復旧

Checkout・Payment・保持期限処理はInventoryの公開契約を使用し、在庫テーブルへ直接書き込まない。Catalogは読取契約を通して表示時の在庫有無を確認する。決済サービスへの通信中はDBトランザクションを保持しない。

旧コードが予約を省略したまま外部決済を開始したり、在庫を確定・解放せず購入状態を進めたりすることはDB制約でも拒否する。移行前のShopify/Preview商品参照を自作在庫へ割り当てない。

本番開始前には、実在庫登録・補充・調整の権限と監査、実Stripeでの照合、結果不明の決済作成の復旧、配送・税・出荷の検証が必要。今回は公開条件や受付停止を解除しない。

## 追補：顧客による取消（2026-09-14）

本番経路のカート削除は、サーバーで本人の購入準備を確認して取り消した後にだけ、ブラウザーのカートを消す。上記の解放の根拠は変えない。

- 決済先の選択前は、既存の行ロック付き取消で予約を解放する。
- Stripe Checkout Session発行済みの場合は、保存済みのSession IDに対してStripeへ失効を要求する。応答またはSessionの再取得で `expired` を確認した場合だけ成功とする。この操作では在庫を解放せず、保存済みIDと一致する署名検証済みの `checkout.session.expired` が従来どおり解放する。
- 決済先を選択したがSession IDを保存していない取引は取り消さず、カートを残す。失効の応答が不明で再取得もできない場合は未確認として障害を記録し、カートを残して再試行を促す。有効なSessionの失効をStripeが拒んだ場合は元のエラーを想定外として記録する。
- 決済手続きが完了したSessionと注文確定後は取り消さない。本番では決済完了後にブラウザーのカートを自動で消していないため、古いカートだけを空にし、注文を取り消していないことを表示する。
- 他の顧客・未ログインの要求では、Stripeへ問い合わせない。Sessionの購入準備ID・モード・IDが一致しない応答は異常として報告する。
- 取消は新規受付の停止フラグに依存しない。停止中でも、顧客は発行済みの決済画面を閉じられる。運営者による一括失効は引き続き別手順とする。
- 処理中に別のカートへ置き換わった場合、ブラウザーは新しいカートを削除しない。
- 2026-09-14追記：カートの内容変更や別の花への入替を保存する場合も、新しいカートを保存する前に、前のカートの購入準備を同じ手順で取り消す。新しいカートは別の要求IDになり、前の予約を引き継がないためである。取り消せない場合は保存せず、前のカートとエラーを残す。決済手続きが完了していた場合は新しいカートを保存し、前の注文を取り消していないことをカートで表示する。

追補を戻す場合は、カート削除とギフト保存からサーバー取消の呼出しを外す。Stripe側で失効したSessionは戻さず、期限切れ通知による解放をそのまま処理する。

## 代替案

支払後だけの在庫減算は同時購入で売り越すため採用しない。外部決済の状況に関係なく期限で予約を解放する案は、支払可能なセッションが残るため採用しない。別サービスやキューでの予約は現状では不要。

## ロールバック

新規受付を止め、Inventory対応ワーカーで進行中の取引を照合する。旧ワーカーへの巻き戻しではDB制約により処理が停止する。予約・数量・移動履歴を削除したり、結果不明の予約を手動で販売可能に戻したりしない。
