# ADR 0021: 問い合わせ回答の連絡手段

- 状態：**採用（2026-09-24）。** 同日、事業者が下記「承認が必要な点」の3点すべてを承認。実際の配信は、メール配信事業者の設定後（既定は無効、ADR 0019と同じ条件）。
- 範囲：顧客がマイページから送った問い合わせ（`customer_requests`）に運営が回答したことを、どうやって顧客へ伝えるか。P1-01、P2-02。

## 背景

顧客はマイページから注文・キャンセル・返品・配送についてご相談を送れる。担当者は専用権限の画面で回答を保存でき、回答はマイページに表示される。文面でも「回答はこの画面に表示します」と説明している。

しかし**回答が保存されたことを顧客に知らせる手段がない**。次の3点が重なっている。

1. 顧客のメールアドレスをBloomBoxのDBに保存していない。Googleログインで保存するのは識別子（`provider_subject`）だけで、`customer_contacts` へ書き込む実装は存在しない。
2. そのため担当者は顧客のメールアドレスを画面で見られない。折り返しの連絡をメールで送ることもできない。回答はマイページが唯一の経路になっている。
3. キャンセル・変更の受付期限はお届け希望日の4日前である。顧客がマイページを見に来るまで回答に気づかないと、期限内に合意できないおそれがある。

購入者宛ての取引通知（注文確認・発送）は既に実装済みで、宛先はStripe Checkoutで購入者が入力したメールアドレスを、注文ごとの暗号化スナップショットから復号して使っている。これは保持期限（180日）で削除される。

## 決定

**注文に紐づく問い合わせに限り、その注文の購入者メールアドレスへ「回答があります」だけを伝える通知を送る。** 個人情報の保存項目は増やさない。

- **送るもの**
  - 件名・本文に回答本文を入れない。「お問い合わせに回答しました。マイページでご確認ください」と、マイページへの経路だけを書く。
  - 注文番号は入れる（購入者自身の注文の事実）。受取人の氏名・住所、贈る言葉、相談本文、回答本文は入れない。
  - 対象は `status` を `REPLIED` にしたときだけ。`CLOSED`（対応完了）では送らない。
- **宛先**
  - 対象の問い合わせに `order_id` があるときだけ送る。宛先はその注文の購入者メールアドレス（ADR 0019と同じ復号経路）。
  - `order_id` のない問い合わせには送らない。マイページの文面で「ご注文に紐づかないお問い合わせは、マイページでご確認ください」と明示する。
  - 受取人には送らない。
- **イベント**
  - 回答の保存と同じトランザクションで `customer.request.replied` をOutboxへ入れる。payloadは `requestId` と `orderId` のみ。メールアドレス・本文は入れない。
  - サポート用ロールにはOutboxへのINSERTだけを許可する（発送管理ロールと同じ方式）。
- **消費・再試行・期限**
  - ADR 0019の既存の消費者に3つ目の種別として追加する。リース、`FOR UPDATE SKIP LOCKED`、冪等キー、最大6回の再試行、48時間の送信期限、有効化条件（`BLOOMBOX_NOTIFICATIONS_ENABLED`）はそのまま適用する。
  - 送信直前に問い合わせを読み直し、`REPLIED` でなくなっていれば送らない。
  - 注文の個人情報が保持期限で削除済みなら宛先がないため、確定スキップ（`NO_BUYER_EMAIL`）として1回で終える。
- **利用目的の整合**
  - プライバシーポリシーの利用目的に「お問い合わせへの回答のご連絡」を含める。決済時に受け取ったメールアドレスを、その注文に関する連絡に使う範囲を超えない。
  - 追加の同意取得は行わない。取引に必要な連絡であり、広告・マーケティングの配信とは分ける。
- **保持**
  - 新しい個人データを保存しない。宛先は既存の注文スナップショットの中だけにあり、注文の保持期限で消える。

## 検討した代替案

- **何もしない（現状維持）**：顧客はマイページを見に来ないと回答に気づかない。期限が4日前にあるため、相談が期限内に完了しないおそれが残る。回答経路が1つだけで、届いた保証もない。
- **回答本文をメールで送る**：**採らない。** 回答には注文・住所・お届け先の事情が書かれうる。メールは受信環境の保護を前提にできず、保持期限の管理もBloomBox側で完結しない。マイページ（認証必須・保持期限あり）に置いたまま、通知は所在だけを伝える。
- **顧客のメールアドレスをDBに保存する（`customer_contacts` を使う）**：注文のない問い合わせにも通知できる。担当者がメールで折り返せるようになり、氏名・メールでの顧客検索（P1-01の残作業）も可能になる。一方で、保存する個人データが増え、保持期間・閲覧権限・削除依頼の扱い・漏えい時の影響が新たに発生する。**販売開始時点では採らない。** 必要性（注文外の問い合わせ件数、メール折り返しの業務要件）が事業判断で確定してから、別ADRで扱う。
- **担当者が個人のメールで返信する**：記録が残らず、宛先の取り違えと個人情報の持ち出しが起きる。採らない。
- **SMS・LINEなど別経路**：連絡先を新たに取得する必要がある。範囲外。

## 影響と切り戻し

- DBスキーマの変更はない。追加はイベント種別と、サポート用ロールへのOutbox INSERT権限のみ。
- 有効化していない環境では何も送らない。`BLOOMBOX_NOTIFICATIONS_ENABLED=false` で止められ、止めている間のイベントは48時間で送信対象から外れる。
- revertすれば通知は消える。回答はマイページに残り、顧客の参照経路は現状のままになる。

## 承認（2026-09-24）

事業者が次の3点を承認した。

1. 注文に紐づく問い合わせの回答を、決済時のメールアドレスへ連絡すること（利用目的への追記を含む）。
2. 注文に紐づかない問い合わせには通知しないこと（マイページのみ）。
3. 顧客のメールアドレスをDBに保存しない判断を、販売開始時点では維持すること。

実装範囲は、イベント追加・テンプレート・消費者の分岐・権限追加・プライバシーポリシーの追記に限る。運用手順は[取引通知](../../operations/NOTIFICATIONS.md)を参照する。
